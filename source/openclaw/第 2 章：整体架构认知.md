# 第 2 章：整体架构认知

> **这一章解决什么问题？**
> 在第 1 章中，你已经知道 OpenClaw 由六大组件构成——Gateway、Agent、Workspace、Skills、Cron、Sandbox。但那只是一张粗略的地图。现在，我们要走进地图中的每一个区域，看清楚每个组件到底做了什么、为什么存在、以及它们之间怎么协作。
> 读完这一章之后，你看到任何 OpenClaw 命令时，都能立刻说出"这条命令操作的是哪个组件、它在系统中处于什么位置"。这就是从"会用命令"到"理解系统"的关键跨越。

---

## 2.1 Gateway 是什么

### 2.1.1 一句话定义

Gateway 是 OpenClaw 的**中枢服务**——一个在本地持续运行的后台进程，负责接收请求、调度 Agent、管理定时任务、记录日志、维护系统状态。

如果你把 OpenClaw 比作一家公司，Gateway 就是**总控室**。所有的指令都先到总控室，总控室决定"这个任务交给谁去做"、"这个定时任务该不该触发了"、"刚才那个任务的日志需要记录下来"。

### 2.1.2 为什么几乎所有能力都围绕 Gateway 展开

这是初学者最容易困惑的一个点：**为什么我执行一个 CLI 命令，背后怎么总是在跟 Gateway 打交道？**

原因是 OpenClaw 的架构设计采用了**客户端-服务端模式**（即使客户端和服务端都在你的电脑上）：

```
你的终端（CLI客户端）
       │
       │  发送请求（通过 WebSocket）
       ▼
Gateway（本地服务端）
       │
       ├── 调度 Agent
       ├── 触发 Cron
       ├── 管理 Sandbox
       ├── 记录 Logs
       └── 返回结果
```

当你在终端输入一条命令（比如让 Agent 执行一个任务），CLI 把你的指令打包成一个请求，通过 WebSocket 发送给 Gateway。Gateway 处理这个请求，调度 Agent 去执行，执行完毕后把结果返回给 CLI，显示在你的终端上。

**这意味着什么？**

1. **Gateway 必须先启动，其他命令才能用。** 这是最基本的前提。如果 Gateway 没有运行，你的 CLI 命令就像打电话给一个关机的手机——没有人接。
2. **Gateway 的健康状态决定了整个系统是否可用。** 这就是为什么 OpenClaw 提供了 `health`、`status`、`doctor` 等命令来检查 Gateway 的状态。
3. **Gateway 崩溃 = 所有正在运行的任务中断。** 这在后续的运维章节（第 14 章）中会详细讲如何预防和恢复。

### 2.1.3 Gateway 在本地运行意味着什么

"本地运行"有几个重要含义：

**优点：**
- **数据不离开你的电脑。** Gateway 处理的所有请求、日志、任务结果都存在本地。这对数据安全和隐私来说是一个很大的优势。
- **不依赖外部服务的稳定性。** 你的 Gateway 不会因为某个云服务宕机而停止工作（模型 API 除外——如果你用的是远程模型，那模型调用仍然依赖网络）。
- **你拥有完全的控制权。** 你可以随时启动、停止、重启 Gateway，查看所有日志，修改所有配置。

**需要注意的：**
- **你的电脑关机 / 睡眠 = Gateway 停止。** 如果你设置了 Cron 定时任务，但你的电脑在那个时间点处于睡眠状态，任务就不会执行。
- **Gateway 消耗系统资源。** 它是一个持续运行的后台进程，虽然通常资源消耗不大，但在任务密集时可能会使用较多 CPU 和内存。
- **不适合共享给其他用户。** 一个 Gateway 实例应该只服务于一个信任的用户。如果你让不信任的人共享你的 Gateway，他们可能通过 Gateway 访问你的文件系统。这在第 3 章（安全观）中会详细讲。

### 2.1.4 Gateway 与其他组件的关系

| 其他组件 | 与 Gateway 的关系 |
|---|---|
| Agent | Gateway 接收任务请求，调度 Agent 执行 |
| Cron | Gateway 内置调度器管理 Cron 任务的触发 |
| Logs | Gateway 记录所有操作日志 |
| Health | `health` 命令检查 Gateway 是否正常运行 |
| Status | `status` 命令查看 Gateway 的当前状态 |
| Doctor | `doctor` 命令诊断 Gateway 及其依赖的潜在问题 |

一个实际场景帮你理解：

> 你设置了一个 Cron 任务："每天 08:00 执行资讯巡检"。到了 08:00，是**Gateway 的内置调度器**检测到"有一个任务到时间了"，然后调度一个 Agent 去执行巡检任务。Agent 执行过程中调用模型推理、调用工具抓取网页、产出结果。所有的执行日志都被 Gateway 记录下来，你之后可以用 `logs` 命令查看。
>
> 如果 Gateway 在 07:59 崩溃了，08:00 的任务就不会被触发——因为没有人去检查"现在是不是到时间了"。

## 2.2 Agent 是什么

### 2.2.1 一句话定义

Agent 是 OpenClaw 中**实际执行任务的工作单元**。你给它一条指令，它通过调用模型（LLM）进行推理、调用工具进行操作，最终产出结果。

### 2.2.2 一次 Agent Turn 的完整流程

"Turn"（轮次）是 Agent 执行任务的基本单位。一次 turn 可以理解为"从接收任务到返回结果的一次完整执行周期"。

让我们用一个真实场景来走一遍完整流程：

**场景：** 你给 Agent 一条指令——"访问 https://example.com/news，提取页面上所有文章的标题和发布日期，保存为 JSON 文件到 /workspace/news-watcher/today.json"。

**Step 1：指令到达**
你在终端输入指令。CLI 将指令发送给 Gateway，Gateway 创建一个新的 Agent Turn。

**Step 2：模型推理（第一轮）**
Agent 把你的指令发送给模型（LLM）。模型分析指令后，决定："我需要先访问这个网页，获取 HTML 内容。"模型生成一个**工具调用请求**——调用 HTTP 请求工具访问目标 URL。

**Step 3：工具执行（第一轮）**
Agent 调用 HTTP 请求工具，实际发出请求，拿到了网页的 HTML 内容。工具把 HTML 内容返回给 Agent。

**Step 4：模型推理（第二轮）**
Agent 把 HTML 内容再发送给模型。模型分析 HTML，提取出所有文章的标题和发布日期，组织成 JSON 格式。模型生成一个新的**工具调用请求**——调用文件写入工具，将 JSON 内容写入指定路径。

**Step 5：工具执行（第二轮）**
Agent 调用文件写入工具，将 JSON 数据写入 `/workspace/news-watcher/today.json`。

**Step 6：任务完成**
模型判断任务已完成，Agent 返回执行结果给 Gateway，Gateway 将结果显示在你的终端上。整个 turn 结束。

用流程图表示：

```
你的指令
   │
   ▼
模型推理："我需要访问网页"
   │
   ▼
工具执行：HTTP GET → 拿到 HTML
   │
   ▼
模型推理："我需要从 HTML 中提取标题和日期，存为 JSON"
   │
   ▼
工具执行：写入 /workspace/news-watcher/today.json
   │
   ▼
模型推理："任务完成了"
   │
   ▼
结果返回给你
```

**关键观察：**

- 一次 turn 中，模型和工具之间可能**来回交互多次**（上面的例子是两轮）。复杂任务可能需要更多轮次。
- 模型的每次推理都有**成本**——如果你用的是远程模型 API（比如 Claude API），每次推理都会消耗 token，产生费用。所以设计好 Agent 的指令可以减少不必要的推理轮次。
- Agent 不会"记住"上一次 turn 的内容（除非你通过 Workspace 或其他机制显式传递上下文）。每次 turn 是一个**相对独立的执行单元**。

### 2.2.3 `agent` 和 `agents` 命令的区别

初学者常常混淆这两个命令：

- **`agent`**（单数）：用来**发起一次 Agent Turn**——即让 Agent 执行一个具体任务。这是你最常用的命令。
- **`agents`**（复数）：用来**管理 Agent 配置**——查看有哪些 Agent、它们的配置是什么、创建新的 Agent 等。

打个比方：`agent` 就是"叫员工去干活"，`agents` 就是"查看员工名册 / 招聘新员工 / 修改员工的职责定义"。

### 2.2.4 默认 Agent 与隔离 Agent

当你第一次使用 OpenClaw 时，系统会有一个默认的 Agent，你可以直接用它来执行任务。但随着你的使用场景增多，你会发现**一个 Agent 做所有事情**不是一个好主意。

为什么？因为不同任务需要不同的权限、不同的工具、不同的输出路径。如果一个 Agent 同时有"读写文件"和"访问网络"和"执行 shell 命令"的权限，那它的攻击面就太大了——一旦它的行为出错（或被恶意指令欺骗），影响范围会很广。

**最佳实践是：按角色创建专门的 Agent。** 比如：

| Agent 名称 | 职责 | 拥有的权限 |
|---|---|---|
| news-watcher | 资讯巡检 | 只读网络访问 + 写入 /workspace/news-watcher/ |
| kanji-collector | 汉字资料采集 | 只读网络访问 + 写入 /workspace/kanji-staging/ |
| course-builder | 课程整理 | 读取 /workspace/course-raw/ + 写入 /workspace/course-output/ |
| prototype-dev | 原型开发 | Sandbox 内运行，完整开发环境 |

这就是第 6 章（Agent 设计方法论）会深入讲解的内容。这里你只需要知道：**Agent 可以有多个，每个 Agent 应该有明确的职责和受限的权限。**

## 2.3 Workspace 是什么

### 2.3.1 一句话定义

Workspace 是 OpenClaw 中的**工作空间隔离单元**，每个 Workspace 对应一个独立的工作目录和上下文环境，让不同类型的任务在物理上和逻辑上互不干扰。

### 2.3.2 为什么要分 Workspace

想象这样一个场景：你让 Agent 抓取汉字检定资料，结果 Agent 因为一个 bug 把输出文件写到了你正在开发的前端项目目录里，覆盖了你的 `package.json`。

这不是假设——在没有目录隔离的环境中，这种事情确实会发生。Agent 的行为受模型推理影响，而模型有时候会犯错（比如误解了你的路径指令）。

Workspace 解决的就是这个问题：**通过把不同任务限制在不同的目录里，确保一个任务的失误不会波及其他区域。**

几个具体的好处：

**降低误操作范围**
如果资讯巡检 Agent 只能写入 `/workspace/news-watcher/`，那它无论怎么出错，也影响不到 `/workspace/kanji-staging/` 里的汉字检定数据。

**方便审计**
当你想检查某个任务的所有产出时，只要去看对应的 Workspace 目录就行了，不用在整个文件系统中搜索。

**方便版本控制**
你可以为每个 Workspace 单独设置 Git 版本控制，这样不同任务的变更历史互不混淆。

**方便做 staging**
每个 Workspace 可以有自己的 staging / validated / production 子目录，形成清晰的数据流转管道。

### 2.3.3 Workspace 与目录权限的关系

Workspace 不仅仅是一个"目录"——它还定义了 Agent 的**访问权限边界**。当你将一个 Agent 绑定到某个 Workspace 时，你可以指定这个 Agent 只能读取或写入该 Workspace 内的文件。

这意味着：

| 配置 | 效果 |
|---|---|
| Agent A → Workspace X（读写） | Agent A 可以读写 /workspace/X/ 下的文件 |
| Agent A → Workspace Y（只读） | Agent A 可以读取 /workspace/Y/ 的文件，但不能修改 |
| Agent A → Workspace Z（无权限） | Agent A 无法访问 /workspace/Z/ 的任何文件 |

这种机制和操作系统的用户权限类似——不同用户只能访问自己有权限的目录。区别在于，这里的"用户"是 Agent，"目录"是 Workspace。

### 2.3.4 推荐的 Workspace 规划

基于在第 0 章定义的使用场景，以下是一个推荐的 Workspace 规划：

```
/workspace/
  ├── news-watcher/       # 资讯巡检
  │   ├── raw/            # Agent 原始产出
  │   ├── daily/          # 每日摘要
  │   └── archive/        # 历史归档
  │
  ├── kanji-staging/      # 汉字检定资料采集
  │   ├── raw/            # 原始抓取数据
  │   ├── structured/     # 结构化后的 JSON/CSV
  │   └── validated/      # 人工审核通过的数据
  │
  ├── course-builder/     # 课程模块化整理
  │   ├── source/         # 原始素材
  │   ├── modules/        # 生成的课程模块
  │   └── drafts/         # 待审核的草稿
  │
  ├── prototype-lab/      # 原型验证
  │   ├── current/        # 当前正在验证的原型
  │   └── archive/        # 已归档的原型
  │
  └── importer/           # 数据库入库中间层
      ├── pending/        # 等待入库的数据
      ├── imported/       # 已入库的数据
      └── rejected/       # 被拒绝的数据
```

> **提醒：你不需要一开始就建立所有 Workspace。** 先建 1～2 个（比如 `news-watcher` 和 `kanji-staging`），把一条流程跑通后，再根据需要扩展。

## 2.4 Sandbox 是什么

### 2.4.1 一句话定义

Sandbox 是 OpenClaw 中基于 **Docker** 的隔离运行环境。它让 Agent 在一个独立的容器中执行操作，即使 Agent 的行为出了问题，也不会影响你的宿主机系统。

### 2.4.2 为什么 Sandbox 不是"高级可选项"

很多人第一次看到 Sandbox 的概念时会想："这是高级功能吧？我先学基础的就够了。"

在纯对话模式下，这个想法没错——如果你只是跟 Agent 聊天问问题，确实不需要 Sandbox。但在 **Operator 模式**下，Agent 会实际执行操作：读写文件、运行脚本、安装依赖包、发起网络请求。这些操作如果直接在你的宿主机上执行，一旦出错，后果可能很严重：

- **Agent 运行了一个有 bug 的脚本** → 可能删除或覆盖你的文件。
- **Agent 安装了一个有问题的依赖包** → 可能破坏你的开发环境。
- **Agent 执行了一个恶意指令**（例如通过被篡改的 skill）→ 可能窃取你的数据或破坏系统。

Sandbox 的作用就像一个**防火隔间**：Agent 在容器里执行操作，容器与你的宿主机是隔离的。即使容器里发生了灾难，你只需要销毁容器、重新创建一个即可——你的宿主机不受影响。

### 2.4.3 什么情况下必须用 Sandbox

| 场景 | 为什么必须用 Sandbox |
|---|---|
| Agent 需要运行你不完全信任的脚本 | 脚本可能有未知的副作用 |
| Agent 需要安装 npm / pip 等依赖包 | 安装过程可能修改全局环境 |
| Agent 执行原型开发任务（写代码 + 运行） | 代码可能有 bug，影响宿主机 |
| Agent 使用第三方 Skills/Plugins | 插件可能有安全漏洞或恶意行为 |

### 2.4.4 什么情况下可以先不用 Sandbox

| 场景 | 为什么可以暂时不用 |
|---|---|
| Agent 只是阅读文件并生成摘要 | 只读操作，不修改任何东西 |
| Agent 只是抓取网页内容并保存到固定目录 | 写入范围被 Workspace 限制 |
| 你在做临时的一次性实验 | 低风险且可快速恢复 |

**但请记住：** "可以暂时不用"不等于"永远不需要用"。随着你的任务变得更复杂、Agent 的权限变得更大，Sandbox 会从"可选"变成"必须"。第 8 章会专门深入讲解 Sandbox 的使用方法和注意事项。

### 2.4.5 Sandbox 的基本原理

Sandbox 基于 Docker 容器技术。如果你不熟悉 Docker，可以这样理解：

> Docker 容器就像一个"一次性虚拟电脑"。你可以在里面装软件、运行程序、创建文件。当你不需要它时，把它销毁就行了——里面的一切都会消失，不会影响你的真实电脑。

OpenClaw 的 Sandbox 就是创建一个这样的容器，让 Agent 在里面执行任务。Agent 以为自己在操作"真实环境"，但实际上它只是在一个隔离的容器里。

```
你的宿主机 (macOS/Linux)
  │
  ├── 你的文件系统（受保护）
  ├── 你的开发环境（受保护）
  │
  └── Docker 容器（Sandbox）
       │
       ├── Agent 在这里执行操作
       ├── 容器内的文件系统（隔离的）
       └── 如果出问题，销毁容器即可
```

> **前提条件：** 使用 Sandbox 需要你的电脑上安装了 Docker。如果你还没有安装，不用着急——第 4 章（安装与运行路径）会告诉你如何安装和配置。

## 2.5 Cron 是什么

### 2.5.1 一句话定义

Cron 是 OpenClaw 内置的**定时任务调度器**，让你可以设置"在指定时间自动触发 Agent 执行任务"。它由 Gateway 的内置调度器管理，支持周期性任务（recurring）和一次性任务（one-shot），并带有运行记录和失败处理能力。

### 2.5.2 定时任务的本质

如果你用过 Linux 的 `crontab`，OpenClaw 的 Cron 在概念上类似——但有几个关键区别：

| 维度 | Linux crontab | OpenClaw Cron |
|---|---|---|
| 调度什么 | Shell 命令 | Agent Turn（Agent 执行任务） |
| 管理方式 | 编辑 crontab 文件 | 通过 CLI 命令或配置管理 |
| 日志记录 | 通常需要自己配置 | 内置运行记录 |
| 失败处理 | 通常需要自己写逻辑 | 内置失败记录和处理机制 |
| 依赖环境 | 操作系统的 cron 服务 | Gateway 的内置调度器 |

### 2.5.3 Cron 适合做什么

**日常资讯巡检**
> "每天 08:00，去 3 个技术博客抓取最新文章标题和摘要，生成一份日报保存到 `/workspace/news-watcher/daily/`。"
>
> 这是 Cron 的经典使用场景：固定时间、固定操作、固定输出。

**定期数据抓取**
> "每周一 10:00，从汉字检定资料网站抓取本周新增的资料页面。"
>
> 结合 Agent 的采集能力和 Workspace 的目录管理，Cron 可以构建一个稳定的数据采集管道。

**周期性变更监控**
> "每天 18:00，检查某个 GitHub 仓库是否有新的 Release。如果有，生成一份变更摘要。"
>
> 这类任务需要 Agent 做一个简单的检查 + 条件判断 + 输出。

### 2.5.4 Cron 不适合一开始就跑什么

**高风险写入操作**
> 不要在你还没有完全验证流程的时候，就用 Cron 让 Agent 自动往数据库里写数据。因为如果 Agent 每天自动跑，但你的采集逻辑有 bug，三天后你可能发现数据库里多了几千条垃圾数据。

**高成本抓取**
> 如果你的 Agent 每次执行需要调用大量模型 API（大量 token 消耗），在用 Cron 自动化之前，先手动跑几次，确认 token 消耗在你的预算范围内。

**需要登录态的复杂交互**
> 需要模拟登录、处理验证码、维护 session 的任务，通常不适合直接 Cron 化——因为这类任务的失败率较高，需要更多的人工干预和调试。

> **尝试节奏建议**：先手动执行 3～5 次，确认结果稳定 → 再设置 Cron 定时运行 → 前几天每天检查输出 → 确认稳定后才放心让它自己跑。

## 2.6 Skills / Plugins / Hooks 的概念边界

### 2.6.1 为什么要理解这三个概念

在 OpenClaw 的生态中，你会频繁遇到 Skills、Plugins、Hooks 这三个词。它们看起来都是"给 Agent 增加能力"的东西，但它们的定位、实现方式、安全风险各不相同。初学者经常把它们搞混，导致使用时犯错。

### 2.6.2 Skills：Agent 的能力包

**Skills 是什么？** Skills 是一组预定义的指令和工具，Agent 可以通过加载 Skills 来获得特定的能力。你可以理解为：Skills 是 Agent 的"能力证书"——一个没有加载任何 Skill 的 Agent 什么也做不了；加载了"文件读写 Skill"后它就能操作文件；加载了"HTTP 请求 Skill"后它就能访问网页。

**Skills 的形式：** Skills 通常以 Markdown 文件的形式存在（描述 Agent 应该如何使用某个工具的指令集），或者是工具配置文件。

**安全提醒：** Skills 目前是社区讨论的重点安全话题。因为 Skills 可以定义 Agent 的行为逻辑，一个恶意的 Skill 可能诱导 Agent 执行你不想要的操作。**第一阶段，只使用内置 Skills 或你自己编写的 Skills，不要盲目安装第三方 Skills。**

### 2.6.3 Plugins：系统级扩展

**Plugins 是什么？** Plugins 是比 Skills 更底层的扩展机制。如果说 Skills 是"教 Agent 怎么用工具"，Plugins 更像是"给 Agent 增加新的工具类型"。

**与 Skills 的区别：**
- Skills 侧重于"指令和流程定义"（属于 prompt 层面）。
- Plugins 侧重于"工具和能力注册"（属于系统层面）。

**第一阶段你需要知道什么？** 你只需要知道 Plugins 存在，但**暂时不需要使用或安装任何第三方 Plugin**。OpenClaw 的内置能力足够覆盖你的第一阶段需求。

### 2.6.4 Hooks：事件钩子

**Hooks 是什么？** Hooks 是一种"在特定事件发生时自动触发某个操作"的机制。比如"当一个 Agent Turn 完成时，自动执行一个后处理步骤"或"当一个 Cron 任务失败时，发送一个通知"。

**与 Cron 的区别：**
- Cron 是"按时间触发"——到了指定时间就执行。
- Hooks 是"按事件触发"——某件事发生后才执行。

**第一阶段你需要知道什么？** 同样，你只需要知道 Hooks 存在即可。第一阶段的自动化需求完全可以通过 Cron 满足，不需要 Hooks。

### 2.6.5 一张"现在用 / 以后用"表

| 能力 | 第一阶段 | 进阶阶段 |
|---|---|---|
| 内置 Skills | ✅ 使用 | 继续使用 |
| 自定义 Skills | ✅ 学习编写简单的 | 编写更复杂的 |
| 第三方 Skills | ❌ 暂不安装 | 经审查后按需安装 |
| Plugins | ❌ 暂不使用 | 按需了解和使用 |
| Hooks | ❌ 暂不使用 | 按需了解和使用 |

4. 低风险 Agent（如 A 和 B）直接在宿主机上运行，只能访问自己的 Workspace。
5. 高风险 Agent（如 C）在 Sandbox 容器里运行，额外增加一层隔离。
6. 所有操作都被 Gateway 的日志系统记录。
7. Cron 任务由 Gateway 的调度器管理，到时间自动触发 Agent。

## 2.8 常见误区

### 误区一："Gateway 就是 Agent"

**现实：** Gateway 和 Agent 是两个完全不同的组件。Gateway 是调度中心，Agent 是执行者。就像公司总控室和一线员工的区别——总控室不直接干活，但没有总控室，员工不知道该干什么。

### 误区二："Workspace 只是一个文件夹"

**现实：** Workspace 不仅是一个文件夹，它还定义了权限边界。当你说"Agent A 的 Workspace 是 /workspace/news-watcher/"时，你不只是指定了一个路径，你还在说"Agent A 的读写权限被限制在这个路径内"。

### 误区三："Sandbox 太麻烦了，我先不用"

**现实：** 对于只读任务确实可以先不用。但一旦 Agent 开始执行写操作（写文件、运行脚本、装依赖），就应该认真考虑 Sandbox。"嫌麻烦"的代价可能是某天 Agent 误操作破坏了你的宿主机环境——到时候的恢复成本远高于一开始配置 Sandbox 的成本。

### 误区四："Cron 设好了就不用管了"

**现实：** Cron 任务需要持续监控——至少在初期。你需要定期检查任务是否按时执行了、输出结果是否正确、是否有失败记录。"设好就不管"是进阶阶段的目标，不是第一阶段应有的心态。

## 2.9 如果这里失败，先检查什么

这一章仍然是概念章，没有需要执行的命令。如果你有理解上的困难：

**"Gateway 的客户端-服务端架构我不太理解"**
→ 你可以想象成：你手上有一个遥控器（CLI），客厅里有一台电视（Gateway）。你按遥控器上的按钮，电视收到信号后执行操作。你的遥控器不能自己播放节目——它只能告诉电视"播这个频道"。

**"Agent Turn 的多轮交互我搞不清楚"**
→ 重新看 2.2.2 节的流程图。关键点是：模型推理和工具执行是**交替进行**的——模型"想一步"，工具"做一步"，然后模型再"想下一步"，直到任务完成。

**"Skills、Plugins、Hooks 我分不清"**
→ 暂时不需要分得很清。第一阶段你只需要关注 Skills（而且只关注内置 Skills）。Plugins 和 Hooks 是进阶概念，等你第一阶段完成后再学也不迟。

## 本章学完后你应该会什么

1. **能画出 OpenClaw 的架构草图**——Gateway 在中间，Agent 在下面，CLI 在上面，Workspace 和 Sandbox 在两侧。
2. **能解释一次 Agent Turn 经历了什么**——从指令到达到结果返回的完整流程。
3. **能说出为什么要分 Workspace**——降低误操作范围、方便审计、方便版本控制。
4. **能判断何时需要 Sandbox**——涉及写操作、运行脚本、安装依赖时应该用。
5. **能理解 Cron 的适用场景**——固定时间、固定操作、固定输出的重复性任务。
