# 第 12 章：数据库中间层与受控入库

> **这一章解决什么问题？**
> 你的数据从采集（第 10 章）到整理（第 11 章）一直待在文件系统里——JSON 文件、CSV 文件、Markdown 文件。这对学习阶段来说足够了。但当你的数据量增长、需要复杂查询、需要多端访问时，你会需要数据库。
> 问题是：**怎么让数据安全地从文件进入数据库？** 你在第 3 章建立了安全观：不让 Agent 直接写正式库。第 7 章设计了 staging → validated → production 的三层流程。这一章把最后一个环节补上——**importer（导入器）和受控入库策略**。
> 这一章非常适合你后面做汉字检定资料库时使用。

## 12.1 为什么不要让 Agent 直接写正式库

### 12.1.1 Schema 漂移

Agent 的输出格式可能在不同次执行间有微妙差异——某次多了一个字段、某次字段名拼写不同、某次数值类型变成了字符串。如果这些差异直接写入数据库：

- 某些插入会因为 Schema 不匹配而失败
- 某些记录会有额外的字段被忽略
- 字段类型不一致导致后续查询出错

### 12.1.2 数据污染

Agent（特别是使用 LLM 的 Agent）可能产生幻觉内容——编造不存在的词组、生成与实际不符的读音。如果这些内容直接进入正式库，你的数据库中就混入了虚假信息，而且你可能很久之后才发现。

### 12.1.3 重复写入

如果幂等性没有做好（第 9 章），Agent 重跑一次可能把已有的数据再写一遍。正式库中出现重复记录，影响查询结果和统计数据。

### 12.1.4 错误更新

如果 Agent 有 UPDATE 权限，它可能在更新一条记录时误改了其他字段。比如你只想更新某个汉字的例句，Agent 可能在同一次操作中"顺便"改了读音——而改错了。

### 12.1.5 来源丢失

如果直接写入数据库而不保留原始 JSON 文件，你就失去了"这条数据是怎么来的"的追溯能力。当你发现某条数据有问题时，无法回溯到原始采集结果来排查原因。

**总结：** 这五个风险不是"理论上可能发生"，而是"在你使用 Agent 的过程中几乎一定会遇到"。每一个都足以成为"不让 Agent 直接写正式库"的理由。

## 12.2 正确的流程

### 12.2.1 七步受控入库流程

```
采集 → staging → 校验 → validated → importer → test DB → production
```

每一步的含义：

**第一步：采集**
Agent 从外部数据源采集原始数据。

**第二步：staging**
原始数据写入 staging 目录为 JSON/CSV 文件。这是 Agent 的输出终点。

**第三步：校验**
你（或校验脚本）检查 staging 中的数据：格式是否正确？必填字段是否完整？内容是否合理？

**第四步：validated**
校验通过的数据移动到 validated 目录。这标志着"这份数据经过了质量检查"。

**第五步：importer**
importer（导入器）读取 validated 目录中的数据文件，按照预定义的规则把数据插入数据库。

**第六步：test DB（测试数据库）**
importer 首先把数据导入测试数据库。你在测试库中确认数据正确后，再导入正式库。

**第七步：production（正式数据库）**
确认无误后，将相同的数据导入正式库。

### 12.2.2 为什么是七步而不是两步

"采集了直接写库"是两步。七步看起来很复杂——但每一步都是一道防线。拿掉任何一步，都会增加出问题时的修复成本：

| 跳过的步骤 | 后果 |
|:---|:---|
| 跳过 staging | 无法查看原始数据，出问题时无法排查 |
| 跳过校验 | 脏数据直接流转到下游 |
| 跳过 validated | 无法区分"审核过的"和"没审核的" |
| 跳过 importer | Agent 直接写库，失去确定性控制 |
| 跳过 test DB | 错误数据直接进入正式库，回滚困难 |

## 12.3 Importer 的作用

### 12.3.1 让写库变成确定性行为

Agent 的行为是概率性的——模型可能每次给出略有不同的输出。但数据库操作必须是确定性的——给定相同的输入，必须产生完全相同的数据库变更。

Importer 就是这个"概率到确定性"的桥梁：

- Agent 的产出（概率性）→ JSON 文件（已确定）→ importer 读取 JSON → 执行确定性的数据库操作

Importer 不使用 LLM，不做推理。它是一段传统的代码（Python 脚本、Node.js 脚本），逻辑完全确定：读取 JSON → 解析字段 → 检查约束 → 插入/更新数据库。

### 12.3.2 把 Agent 的自由度收缩到中间产物层

通过这个设计，Agent 的"自由度"被限制在了 JSON 文件层面。它可以自由地决定 JSON 里写什么内容——但它不能直接影响数据库。即使 Agent 产出了完全错误的数据，最坏的结果也只是 staging 目录里多了一个错误的 JSON 文件——删掉就好了。

### 12.3.3 Importer 的基本结构

一个最简单的 importer 脚本长这样（伪代码）：

```python
import json
import sqlite3

def import_data(json_path, db_path):
    # 1. 读取 JSON 文件
    with open(json_path) as f:
        records = json.load(f)
    
    # 2. 连接数据库
    conn = sqlite3.connect(db_path)
    cursor = conn.cursor()
    
    # 3. 逐条处理
    imported = 0
    skipped = 0
    errors = 0
    
    for record in records:
        # 4. 检查必填字段
        if not record.get("kanji") or not record.get("level"):
            errors += 1
            continue
        
        # 5. 检查是否已存在（去重）
        cursor.execute(
            "SELECT id FROM kanji WHERE kanji = ? AND level = ?",
            (record["kanji"], record["level"])
        )
        if cursor.fetchone():
            skipped += 1
            continue
        
        # 6. 插入记录
        cursor.execute(
            "INSERT INTO kanji (kanji, level, on_reading, kun_reading) VALUES (?, ?, ?, ?)",
            (record["kanji"], record["level"],
             json.dumps(record.get("on_reading", [])),
             json.dumps(record.get("kun_reading", [])))
        )
        imported += 1
    
    # 7. 提交事务
    conn.commit()
    conn.close()
    
    # 8. 输出统计
    print(f"导入完成: {imported} 条新增, {skipped} 条跳过, {errors} 条错误")
```

这段代码没有任何 AI 成分。它是纯粹的、确定性的数据操作。

## 12.4 测试库与正式库

### 12.4.1 为什么先 test DB

即使你的 importer 逻辑看起来正确，第一次运行时也可能遇到预期之外的问题：

- 某个字段的长度超过了数据库列的限制
- 某些特殊字符导致 SQL 执行错误
- 去重逻辑有漏洞，产生了重复记录
- 外键约束不满足

让这些问题发生在测试库里，而不是正式库里。

### 12.4.2 如何做抽样核验

导入测试库后，做以下检查：

**数量核验：**
```sql
-- 导入了多少条记录？和 JSON 文件中的记录数一致吗？
SELECT COUNT(*) FROM kanji;
```

**抽样核验：**
```sql
-- 随机抽取 5 条记录，人工检查内容是否正确
SELECT * FROM kanji ORDER BY RANDOM() LIMIT 5;
```

**极端值检查：**
```sql
-- 有没有异常的字段值？
SELECT * FROM kanji WHERE LENGTH(kanji) > 1;  -- 汉字字段应该是单个字符
SELECT * FROM kanji WHERE level NOT IN ('1級', '準1級', '2級', ...);  -- 级别值是否合法
```

**重复检查：**
```sql
-- 有没有重复记录？
SELECT kanji, level, COUNT(*) as cnt FROM kanji GROUP BY kanji, level HAVING cnt > 1;
```

### 12.4.3 如何做回滚

如果测试库中发现了问题，最简单的回滚方式：**直接删除测试库，重新创建。** 测试库就是用来"毁了重来"的。

```bash
# 删除测试库
rm test_kanji.db

# 重新创建（执行建表脚本）
sqlite3 test_kanji.db < schema.sql

# 修复问题后重新导入
python importer.py validated/clean-2025-01-15.json test_kanji.db
```

这就是为什么测试库不存放重要数据——它可以随时被销毁和重建。

## 12.5 你的第一版入库策略

### 12.5.1 先只入测试库

在你的第一版策略中，importer 只向测试库写入。正式库暂时不碰。

等你对整个流程有信心了——importer 跑了 10 次没有出问题、数据质量稳定、Schema 不再频繁变更——再考虑建立正式库。

### 12.5.2 先只写少量样本

不要第一次就把所有数据导入测试库。先导入 10 条记录，仔细检查每一条。确认无误后导入 100 条，再抽查。确认无误后再导入全量数据。

**漏斗方法：**
```
10 条 → 全量人工检查 → 有问题即修复
100 条 → 抽样检查 → 有问题即修复
全量 → 统计检查 → 有问题即修复
```

### 12.5.3 先只覆盖单表

如果你的数据涉及多个表（比如 `kanji` 表、`compounds` 表、`examples` 表），先只做一个表的导入流程。跑通后再扩展到其他表。

当你能稳定地把 `kanji` 表的数据从 JSON → 测试库跑通后，再增加 `compounds` 表、再增加 `examples` 表——逐步扩展。

### 12.5.4 先保留原始 JSON

即使数据已经成功导入了数据库，也不要立刻删除原始 JSON 文件。至少保留 30 天。

原因：

- 如果发现数据库中某条记录有问题，可以回溯到原始 JSON 查看原始值
- 如果需要重新导入（比如 Schema 变更了），原始 JSON 就是重新导入的数据源
- JSON 文件的存储成本极低，没有删除的必要

## 12.6 如果这里失败，先检查什么

**"Importer 报错 'column not found' 或 'type mismatch'"**
→ JSON 文件中的字段名或类型与数据库 Schema 不匹配。对比 JSON 中的键名和数据库表的列名，检查大小写和拼写。检查值的类型（字符串 vs 数值）。

**"导入后发现有重复记录"**
→ Importer 的去重逻辑有问题。检查去重用的主键组合是否正确。可能需要在数据库层面添加唯一约束。

**"导入成功但某些字段是空的"**
→ JSON 中该字段可能用了不同的键名（比如 `on_reading` vs `onReading`），导致 importer 找不到对应值。统一 JSON 的键名格式。

**"测试库和 JSON 文件中的记录数不一致"**
→ 可能有些记录因为校验失败被跳过了。检查 importer 的错误日志，看看哪些记录被跳过了、原因是什么。

**"不确定该用什么数据库"**
→ 学习阶段用 SQLite。零配置、文件型数据库、不需要安装额外服务。当数据量大到 SQLite 性能不够时（通常是几十 GB 级别），再考虑 PostgreSQL。
