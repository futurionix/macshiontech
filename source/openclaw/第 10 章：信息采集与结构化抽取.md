# 第 10 章：信息采集与结构化抽取

> **这一章解决什么问题？**
> 你已经有了 Agent 设计框架（第 6 章）、目录结构（第 7 章）、隔离环境（第 8 章）和定时调度能力（第 9 章）。现在是你的采集员第一次"真正干活"的时候了。
> 信息采集不只是"抓取网页"。它包含一个完整的链路：确定数据源 → 评估可靠性 → 抓取内容 → 提取字段 → 标准化格式 → 质量控制 → 保存。每个环节都可能出问题，每个环节都需要设计。
> 这一章以汉字检定资料采集为主要场景，但方法论适用于你的所有采集需求——资讯动态、产品信息、教育资料、API 数据。

---

## 10.1 采集任务的本质

### 10.1.1 采集不是"爬虫"

当你听到"信息采集"时，可能首先想到的是"写一个爬虫"。但在 OpenClaw 的体系下，采集是一个更广义的概念——Agent 利用它的工具能力（网络访问、文件读取等）从外部数据源获取信息，并把非结构化的信息转换为结构化的数据。

Agent 不是传统意义上的爬虫。它的优势不在于高并发抓取，而在于**理解内容并提取结构化字段**。传统爬虫需要你用 CSS 选择器或 XPath 来定位页面元素——一旦网页改版，选择器就失效了。Agent 可以理解页面内容的语义，即使页面结构变化了，只要信息还在它就能提取。

### 10.1.2 采集的六个环节

```
搜索 → 定位源 → 抓取 → 抽取字段 → 标准化 → 保存
```

**搜索（Search）：** 找到包含目标信息的数据源。这一步通常由你（人类）来做——你决定从哪些网站、RSS 源、API 来获取数据。

**定位源（Locate）：** 确定具体的页面 URL、API endpoint、RSS 地址。把这些信息写入配置文件（`sources.json`）。

**抓取（Fetch）：** Agent 访问数据源，获取原始内容（HTML、JSON、XML 等）。

**抽取字段（Extract）：** Agent 从原始内容中提取出你需要的结构化字段——标题、日期、作者、正文等。这是 Agent 最擅长的环节。

**标准化（Normalize）：** 把提取出的字段统一为一致的格式——日期统一为 ISO 8601、文本去除多余空白、URL 补全为绝对路径等。

**保存（Store）：** 把结构化数据写入 staging 目录的 JSON/CSV 文件。

## 10.2 采集源评估

### 10.2.1 为什么要评估数据源

不是所有数据源都值得采集。在你开始写采集配置之前，先回答以下问题：

- 这个数据源的信息是否可靠？
- 这个数据源是否允许自动化访问？
- 这个数据源的稳定性如何？会不会经常改版或下线？
- 获取这个数据源的数据是否有法律或道德风险？

### 10.2.2 数据源类型及评估

#### 官网
**可靠性：** 高。官方信息是最权威的来源。
**稳定性：** 中高。官网可能改版，但核心信息通常会保留。
**示例：** 汉字检定协会官网的考试大纲、级别说明。
**注意：** 很多官网不提供 API，抓取 HTML 页面时需注意对方的 robots.txt 和使用条款。

#### 公开资料页
**可靠性：** 中高。取决于维护者。
**稳定性：** 中。个人维护的资料页可能随时停更。
**示例：** 教育机构的公开课程页面、开源资料库。

#### 论坛 / 博客
**可靠性：** 中低。用户生成内容，质量参差不齐。
**稳定性：** 低。帖子可能被删除、博客可能停运。
**示例：** 学习者分享的汉字检定备考经验。
**注意：** 需要做内容质量过滤。

#### 二手资料
**可靠性：** 低。信息经过转手可能失真。
**稳定性：** 不确定。
**建议：** 如果可能，追溯到原始来源。使用二手资料时标注来源类型。

#### 数据库镜像 / API
**可靠性：** 高（如果是官方 API）。
**稳定性：** 高。API 通常有版本管理。
**示例：** 字典 API、教育数据开放接口。
**注意：** 注意 API 的调用频率限制和费用。

### 10.2.3 版权与可靠性边界

**核心原则：** 只采集公开可访问的信息。不要突破付费墙、不要绕过登录限制、不要违反数据源的使用条款。

如果你不确定某个数据源是否允许自动化采集——查看它的 `robots.txt`（如果是网站）和使用条款（Terms of Service）。如果明确禁止自动化采集，不要用。

**对于学习用途的灰色地带：** 用 Agent 抓取一些公开的学习资料供个人使用，在道德和法律上的风险通常较低。但如果你打算把采集到的数据用于商业用途或公开发布，必须确保你有合法的使用权。

## 10.3 字段建模

### 10.3.1 什么叫字段

字段是结构化数据的最小单元。一条"汉字检定资料"记录可能包含以下字段：

```json
{
  "kanji": "鬱",
  "level": "1級",
  "on_reading": ["ウツ"],
  "kun_reading": ["ふさ.ぐ", "しげ.る"],
  "compounds": ["鬱病", "鬱蒼"],
  "example_sentence": "鬱蒼とした森林が広がっている。",
  "source_type": "official",
  "source_url": "https://example.com/kanji/鬱",
  "fetched_at": "2025-01-15T08:00:00Z",
  "validation_status": "pending"
}
```

每个键值对就是一个字段。字段设计决定了你的数据能承载多少信息、能被多灵活地查询和使用。

### 10.3.2 什么叫 Schema

Schema 是字段的定义规范——每个字段叫什么名字、是什么类型、是否必填、有什么约束。

```json
{
  "kanji": { "type": "string", "required": true, "description": "汉字" },
  "level": { "type": "string", "required": true, "enum": ["1級", "準1級", "2級", "準2級", "3級", "4級", "5級", "6級", "7級", "8級", "9級", "10級"] },
  "on_reading": { "type": "array", "items": "string", "required": false, "description": "音読み" },
  "kun_reading": { "type": "array", "items": "string", "required": false, "description": "訓読み" },
  "compounds": { "type": "array", "items": "string", "required": false, "description": "熟語" },
  "example_sentence": { "type": "string", "required": false, "description": "例文" },
  "source_type": { "type": "string", "required": true, "enum": ["official", "community", "secondary"] },
  "source_url": { "type": "string", "required": true, "description": "来源 URL" },
  "fetched_at": { "type": "string", "format": "iso8601", "required": true, "description": "抓取时间" },
  "validation_status": { "type": "string", "required": true, "enum": ["pending", "validated", "rejected"] }
}
```

为什么要先定义 Schema？因为 Schema 就是你和 Agent 之间的"合同"——Agent 的产出必须符合这个格式。没有 Schema，Agent 每次的输出格式可能不一样，下游的校验、导入流程全都无法自动化。

### 10.3.3 来源字段与置信度

并非所有字段的来源都一样可靠。有些字段来自官方资料（高置信度），有些来自社区贡献（中置信度），有些来自 Agent 推理（低置信度）。

在数据中标注来源类型，可以帮助你在后续审核时知道"这个字段的值能不能信"。

```json
{
  "kanji": "鬱",
  "level": "1級",
  "level_source": "official",
  "on_reading": ["ウツ"],
  "on_reading_source": "official",
  "example_sentence": "彼は鬱な気分だった。",
  "example_sentence_source": "agent_generated"
}
```

标记了 `agent_generated` 的字段就知道这是模型产出的，需要人工确认。标记了 `official` 的字段可以有更高的信任度。

### 10.3.4 版本信息

采集是一个持续的过程。同一个汉字的信息可能被多次采集、多次更新。版本信息帮你追溯数据的演变：

```json
{
  "kanji": "鬱",
  "version": 2,
  "first_fetched_at": "2025-01-10T08:00:00Z",
  "last_updated_at": "2025-01-15T08:00:00Z",
  "update_reason": "added example sentence from new source"
}
```

## 10.4 汉字检定资料的字段设计

这一节是上面方法论的具体应用。以下是汉字检定资料的推荐字段设计：

### 10.4.1 核心字段

| 字段名 | 类型 | 必填 | 说明 |
|:---|:---|:---|:---|
| `kanji` | string | 是 | 汉字本体 |
| `level` | string | 是 | 检定级别 |
| `on_reading` | string[] | 否 | 音読み列表 |
| `kun_reading` | string[] | 否 | 訓読み列表 |
| `compounds` | string[] | 否 | 常见熟語 |
| `example_sentence` | string | 否 | 例句 |

### 10.4.2 元数据字段

| 字段名 | 类型 | 必填 | 说明 |
|:---|:---|:---|:---|
| `source_type` | string | 是 | 数据来源类型（official / community / secondary） |
| `source_url` | string | 是 | 数据来源 URL |
| `fetched_at` | string | 是 | 抓取时间（ISO 8601） |
| `validation_status` | string | 是 | 校验状态（pending / validated / rejected） |

### 10.4.3 完整示例

```json
{
  "kanji": "鬱",
  "level": "1級",
  "on_reading": ["ウツ"],
  "kun_reading": ["ふさ.ぐ", "しげ.る", "うっ.する"],
  "compounds": ["鬱病", "鬱蒼", "鬱金", "憂鬱"],
  "example_sentence": "鬱蒼とした森林が広がっている。",
  "source_type": "official",
  "source_url": "https://example.com/kanji/鬱",
  "fetched_at": "2025-01-15T08:00:00Z",
  "validation_status": "pending"
}
```

## 10.5 为什么要先写到 JSON / CSV

### 10.5.1 便于抽检

JSON 文件是人类可读的格式。你可以直接用文本编辑器打开，快速浏览几条记录来判断数据质量。如果直接写入数据库，你需要连接数据库、写查询语句才能看到数据——门槛高得多。

### 10.5.2 便于比对

当你优化了采集逻辑后，想比较新旧两次的采集结果——用 `diff` 命令或 JSON 比较工具就能轻松对比两个 JSON 文件。如果数据在数据库里，比对操作要复杂得多。

### 10.5.3 便于重放

如果你发现某次采集的数据有问题，想重新处理——JSON 文件还在 staging 目录里，你可以直接用它作为输入重新跑清洗和整理流程。如果数据已经直接写入了数据库，你可能需要先删除错误数据、再重新采集。

### 10.5.4 便于改 Schema

在早期阶段，你的字段设计可能会经常调整——增加新字段、修改字段类型、更换字段名。如果数据在 JSON 文件中，Schema 变更就是编辑 JSON 的事。如果数据在数据库中，Schema 变更涉及数据库迁移——复杂度高得多。

**总结：** JSON/CSV 是你在学习阶段和探索阶段的"安全缓冲区"。等你的 Schema 稳定了、数据流程成熟了，再考虑通过 importer 导入数据库（第 12 章）。

## 10.6 采集质量控制

### 10.6.1 缺失字段

**问题：** Agent 提取的记录中某些必填字段是空的。比如一条汉字记录没有 `on_reading` 字段。

**原因：** 数据源确实没有这个信息，或者 Agent 没能从内容中识别出来。

**处理：**
- 区分"数据源没有"和"Agent 没提取到"：如果数据源确实没有，字段设为 null 并标注原因；如果 Agent 没提取到，记录为错误案例，优化 Prompt 或换更强的模型。
- 在校验阶段检查必填字段是否完整。

### 10.6.2 重复记录

**问题：** 同一个汉字被重复采集了多次。

**原因：** 多次采集之间没有去重，或者不同数据源有重叠。

**处理：**
- 基于主键（`kanji` + `level`）去重
- 多个来源的同一条记录，选择可靠性最高的来源作为主记录，其他来源作为补充

### 10.6.3 来源不一致

**问题：** 不同数据源对同一个汉字的信息不一致。比如 A 源说某个汉字是 2 级，B 源说是 3 级。

**处理：**
- 优先采信官方数据源的信息
- 标注冲突，留待人工判断
- 不要自动用一个覆盖另一个——保留两个版本的信息

### 10.6.4 格式污染

**问题：** 提取的字段中包含非预期的内容——HTML 标签、特殊字符、广告文本等。

**处理：**
- 在标准化阶段清洗：去除 HTML 标签、trim 空白、移除非预期字符
- 对于日语内容，注意全角/半角的统一

### 10.6.5 时间戳缺失

**问题：** 某些记录没有 `fetched_at` 字段，无法追溯采集时间。

**处理：**
- 在 Agent 的输出 Schema 中将 `fetched_at` 设为必填
- 如果 Agent 忘记填写，在保存阶段用当前时间补填，并在日志中记录

## 10.7 如果这里失败，先检查什么

**"Agent 抓取的页面内容是空的或者是乱码"**
→ 检查目标页面是否需要 JavaScript 渲染（Agent 可能只拿到了空的 HTML 骨架）。检查页面编码。检查是否被反爬机制拦截了。

**"Agent 提取的字段全是 null"**
→ 检查 Agent 的 Prompt 是否正确描述了预期的字段和格式。手动查看原始页面内容，确认信息确实存在。可能需要更强的模型或更精确的 Prompt。

**"输出的 JSON 格式不对，无法被解析"**
→ 在 Prompt 中强调输出必须是合法 JSON。提供一个输出示例。如果模型持续输出非法 JSON，考虑用后处理脚本修复常见格式问题（如多余的逗号、缺少引号等）。

**"采集速度太慢"**
→ 如果是模型推理慢 → 换响应更快的模型或减少每次处理的数据量。如果是网络抓取慢 → 检查网络连接和目标服务器的响应时间。不要通过提高并发来解决——对数据源的高并发访问可能导致你被封禁。
