# 第 5 章：命令行总览与命令分层理解

> **这一章解决什么问题？**
> OpenClaw 的命令行工具包含数十个子命令。如果你打开 `claw --help`，看到一长串命令列表，很容易产生"这么多命令要怎么背"的焦虑。
> 这一章帮你做一件事：**把所有命令按"系统职责"分层，让你知道每一层负责什么。** 你不需要一次性记住所有命令——你只需要知道"我的需求属于哪一层"，然后去那一层里找对应的命令就行。
> 读完这一章，你面对 `claw --help` 时不会再慌。你会知道哪些命令现在就需要学，哪些可以等到用到再查。

---

## 5.1 为什么不能背所有命令

### 5.1.1 命令是按系统职责分层的

OpenClaw 不是一个"做一件事"的工具。它是一个完整的 Agent 运行平台，涵盖了从基础运维到任务调度、从安全管理到分布式协作的多个层面。每个子命令都属于某个层面——脱离了层面去理解单个命令，就像脱离了上下文去背单词，效率很低。

把命令按层分好后，你会发现：

- **有些层你现在就会用到**（运行面、代理面）
- **有些层你很快会用到**（隔离面、调度面、配置面）
- **有些层你可以等到具体需求出现再学**（安全面的部分命令、分布式命令）

### 5.1.2 学习应按"场景"而不是按 help 顺序

如果你按照 `claw --help` 输出的字母顺序去学习命令，你会先碰到 `agent`、再碰到 `approvals`、然后是 `channels`——这完全不符合学习的逻辑。

正确的学习方式是按场景驱动：

| 你想做什么 | 涉及的层 | 先学哪些命令 |
|:---|:---|:---|
| 让 Gateway 跑起来 | 运行面 | `gateway`, `health`, `status` |
| 跑一个任务看看结果 | 代理面 | `agent`, `agents` |
| 把高风险任务隔离 | 隔离面 | `sandbox` |
| 让任务定时自动跑 | 调度面 | `cron` |
| 调整系统配置 | 配置面 | `configure`, `config` |
| 管理密钥和审批 | 安全面 | `secrets`, `approvals`, `security` |

下面我们逐层来看。

## 5.2 运行面命令

运行面的命令负责 Gateway 的生命周期管理和健康监控。这是你最先接触、也是最常使用的一组命令。

### 5.2.1 `gateway`

**用途：** 管理 Gateway 的启动、停止、重启。

```bash
# 启动
claw gateway start

# 停止
claw gateway stop

# 重启（等同于 stop + start）
claw gateway restart
```

Gateway 是整个系统的中枢。所有 Agent 请求都通过 Gateway 路由。如果 Gateway 没有运行，你什么都做不了。

**你已经在第 4 章用过这个命令了。**

### 5.2.2 `health`

**用途：** 快速检查 Gateway 是否存活。

```bash
claw health
```

这是最简单的检查——它只回答一个问题："Gateway 还活着吗？"

返回正常说明 Gateway 在运行。返回异常说明 Gateway 挂了或者无法连接。

**使用时机：** 当你不确定 Gateway 是否还在运行时，第一个跑的命令。

### 5.2.3 `status`

**用途：** 查看 Gateway 的详细运行状态。

```bash
claw status
```

比 `health` 返回更多信息：已注册的 Agent 数量、活跃任务数、运行时长、内存使用、模型连接状态等。

**使用时机：** 当 `health` 返回正常但系统行为异常时（比如任务不响应），用 `status` 看更详细的信息。

### 5.2.4 `logs`

**用途：** 查看系统日志。

```bash
# 查看最近日志
claw logs

# 实时跟踪日志
claw logs --follow

# 只看错误级别
claw logs --level error
```

日志是你排障的核心数据源。只有在日志里才能看到每个请求的详细处理过程、错误原因和堆栈信息。

**使用时机：** 几乎任何时候。学习阶段建议每次跑完任务后都看一下日志。

### 5.2.5 `doctor`

**用途：** 运行全面的系统诊断。

```bash
claw doctor
```

`doctor` 会检查：

- 配置文件是否合法
- 依赖是否满足（如 Docker 是否安装、模型是否可连接）
- 版本兼容性
- 常见的配置错误模式

**使用时机：** 当你遇到无法通过 `health`/`status`/`logs` 定位的问题时。或者当你做了重大配置变更后，跑一次 `doctor` 确认没有引入新问题。

### 5.2.6 运行面命令小结

```
你的 Gateway 正常吗？
├── 快速检查 → claw health
├── 详细状态 → claw status  
├── 看发生了什么 → claw logs
├── 全面诊断 → claw doctor
└── 重启试试 → claw gateway restart
```

## 5.3 代理面命令

代理面的命令负责 Agent 的管理和任务执行。这是你使用 OpenClaw 完成实际工作的核心命令组。

### 5.3.1 `agent`

**用途：** 执行 Agent 相关操作——发起任务、查看 Agent 详情等。

```bash
# 发起一次 Agent 任务
claw agent run --task "抓取今天的 AI 编程新闻"

# 查看某个 Agent 的详细信息
claw agent info <agent-name>
```

`agent run` 是你最常用的命令之一。你在第 4 章已经用它跑过第一次任务了。

**重要概念：** 一次 `agent run` 执行的是一次 "Turn"——Agent 接收指令、推理、使用工具、产出结果、Turn 结束。一个复杂任务可能需要多个 Turn（Agent 会在一个 Turn 中完成多个步骤，或者你分多次下达指令）。

### 5.3.2 `agents`

**用途：** 管理多个 Agent——列出、创建、删除、修改 Agent 定义。

```bash
# 列出所有已定义的 Agent
claw agents list

# 查看某个 Agent 的配置
claw agents show <agent-name>
```

注意 `agent`（单数）和 `agents`（复数）的区别：

- `agent` → 执行层面的操作（"让某个 Agent 干活"）
- `agents` → 管理层面的操作（"管理 Agent 的定义和配置"）

你在第 6 章设计 Agent 时会大量使用 `agents` 命令。

---

## 5.4 隔离面命令

### 5.4.1 `sandbox`

**用途：** 管理 Sandbox（Docker 容器隔离环境）。

```bash
# 查看 Sandbox 状态
claw sandbox status

# 查看可用的 Sandbox 配置
claw sandbox list
```

Sandbox 是 OpenClaw 的安全隔离机制。在第 3 章中你已经理解了为什么高风险 Agent 需要放在 Sandbox 中运行——`sandbox` 命令就是管理这些容器环境的入口。

**注意：** 使用 `sandbox` 命令需要你的机器上安装了 Docker。如果你还没有安装 Docker，不要急——第 8 章会详细讲 Sandbox 的配置和使用。

**使用时机：** 当你需要为 Agent 创建、管理或排查沙盒环境时。

---

## 5.5 调度面命令

### 5.5.1 `cron`

**用途：** 管理定时任务。

```bash
# 列出所有定时任务
claw cron list

# 查看某个定时任务的状态
claw cron status <job-name>

# 查看定时任务的执行记录
claw cron history <job-name>
```

Cron 是让 Agent 从"你手动发起"变成"系统自动触发"的关键。比如"每天早上 8 点抓取 AI 编程动态"、"每周一汇总本周的汉字学习进展"——这些都通过 `cron` 命令来配置和管理。

**使用时机：** 第 9 章会详细讲定时任务的设计和配置。现在你只需要知道"有这么一组命令用来管理定时任务"就够了。

---

## 5.6 配置面命令

### 5.6.1 `configure`

**用途：** 以交互或参数方式修改系统配置。

```bash
# 交互式修改配置
claw configure

# 修改特定配置项
claw configure --set model.default=gpt-4
```

`configure` 是对配置的"高层操作"——它知道配置的结构和约束，会帮你做合法性校验。

### 5.6.2 `config`

**用途：** 直接查看或编辑配置文件。

```bash
# 查看当前配置
claw config show

# 开配置文件编辑
claw config edit
```

`config` 是对配置的"底层操作"——直接与 YAML 文件打交道。

**`configure` vs `config` 的选择：**

| 场景 | 用哪个 |
|:---|:---|
| 不确定配置项叫什么名字 | `configure`（交互式引导） |
| 知道要改什么、想快速改 | `config`（直接编辑） |
| 做批量配置变更 | `config`（编辑 YAML 文件） |

## 5.7 安全面命令

安全面的命令负责密钥管理、操作审批、安全审计。

### 5.7.1 `security`

**用途：** 安全相关的综合管理命令。

```bash
# 查看安全状态概览
claw security status

# 运行安全审计
claw security audit
```

`security` 命令帮你检查当前系统的安全状态——哪些 Agent 有什么权限、是否存在过大的权限授予、是否有未审计的操作等。

### 5.7.2 `approvals`

**用途：** 管理操作审批。

```bash
# 查看待审批的操作
claw approvals pending

# 审批一个操作
claw approvals approve <operation-id>

# 拒绝一个操作
claw approvals deny <operation-id>
```

Approvals 机制让你可以要求某些高风险操作（比如 Agent 要删除文件、执行 Shell 命令）在执行前必须经过你的手动确认。这是第 3 章中提到的"人工闸门"的技术实现。

### 5.7.3 `secrets`

**用途：** 管理敏感信息（API Key、Token、密码等）。

```bash
# 列出已存储的密钥（不会显示实际值）
claw secrets list

# 添加一个密钥
claw secrets set <name> <value>

# 删除一个密钥
claw secrets delete <name>
```

**为什么要用 `secrets` 而不是把 API Key 放在配置文件里？** 因为配置文件可能被版本控制（Git）、被日志输出、被其他程序读取。`secrets` 系统专门用于安全地存储和访问敏感信息，不会在日志或配置中明文出现。

**使用时机：** 第 15 章会详细讲安全审计和密钥管理。现阶段如果你的 onboarding 流程已经帮你设置了 API Key，暂时不需要手动操作 `secrets` 命令。

## 5.8 暂时后置的命令

以下命令属于高级功能或特定场景。第一阶段学习中你不需要它们，但知道它们存在可以帮助你建立全景认知。

### 5.8.1 通信层命令

| 命令 | 用途 | 何时学 |
|:---|:---|:---|
| `channels` | 管理消息通道（Slack、Webhook 等） | 当你需要让 Agent 输出到外部系统时 |
| `message` | 发送或查看消息 | 与 channels 配合使用 |

### 5.8.2 设备与配对命令

| 命令 | 用途 | 何时学 |
|:---|:---|:---|
| `devices` | 管理连接的设备 | 多设备协作场景 |
| `directory` | 管理服务目录与发现 | 分布式部署时 |
| `pairing` | 设备配对 | 多设备协作场景 |

### 5.8.3 扩展与集成命令

| 命令 | 用途 | 何时学 |
|:---|:---|:---|
| `webhooks` | 管理 Webhook 回调 | 与外部系统集成时 |
| `plugins` | 管理插件 | 第一阶段不建议用第三方插件（第 3 章安全原则） |
| `hooks` | 管理生命周期钩子 | 需要在 Agent 执行流程中插入自定义逻辑时 |

### 5.8.4 分布式命令

| 命令 | 用途 | 何时学 |
|:---|:---|:---|
| `node` | 管理单个节点 | 多机部署时 |
| `nodes` | 管理节点集群 | 多机部署时 |

### 5.8.5 其他命令

| 命令 | 用途 | 何时学 |
|:---|:---|:---|
| `memory` | 管理 Agent 的记忆系统 | 需要 Agent 在多次执行间保持上下文时 |

**这些命令你现在不需要学。** 但当你在后续章节遇到某个概念（比如第 17 章讲 channels 和 plugins），或者你有了具体需求时，回到这一节查阅就好。

## 5.9 命令分层全景图

把所有命令按层画一张图：

```
┌─────────────────────────────────────────────┐
│               OpenClaw 命令分层              │
├──────────┬──────────────────────────────────┤
│ 运行面    │ gateway, health, status,         │
│          │ logs, doctor                      │
│          │ → 管 Gateway 的生死和健康          │
├──────────┼──────────────────────────────────┤
│ 代理面    │ agent, agents                    │
│          │ → 管 Agent 的定义和执行            │
├──────────┼──────────────────────────────────┤
│ 隔离面    │ sandbox                          │
│          │ → 管容器隔离环境                   │
├──────────┼──────────────────────────────────┤
│ 调度面    │ cron                             │
│          │ → 管定时任务                       │
├──────────┼──────────────────────────────────┤
│ 配置面    │ configure, config                │
│          │ → 管系统配置                       │
├──────────┼──────────────────────────────────┤
│ 安全面    │ security, approvals, secrets     │
│          │ → 管权限、审批、密钥               │
├──────────┼──────────────────────────────────┤
│ 高级/     │ channels, message, devices,      │
│ 后置     │ directory, pairing, webhooks,     │
│          │ plugins, hooks, memory,           │
│          │ node, nodes                       │
│          │ → 第一阶段不需要                   │
└──────────┴──────────────────────────────────┘
```

**你现在需要掌握的层：** 运行面 + 代理面（共 7 个命令）。

**你很快会用到的层：** 隔离面 + 调度面 + 配置面（共 4 个命令）。

**可以后置的层：** 安全面的部分命令 + 高级命令（等到具体需求出现再学）。

## 5.10 如果这里失败，先检查什么

这一章是概念章，没有需要"跑通"的操作。但你可能有以下疑惑：

**"我运行了某个命令但报错说不存在"**
→ 检查你的 OpenClaw 版本。不同版本可能有不同的命令集。运行 `claw --version` 确认版本，然后查阅对应版本的文档确认命令是否存在。

**"某个命令的参数我不知道怎么写"**
→ 使用 `claw <命令> --help` 查看详细用法。比如 `claw agent run --help` 会列出所有可用参数。

**"分层感觉模糊，不确定我的需求属于哪一层"**
→ 回到上面的全景图，用排除法：如果你的需求不涉及 Gateway 运维（不是运行面）、不涉及定时（不是调度面）、不涉及安全（不是安全面）——那大概率是代理面或配置面的事情。
