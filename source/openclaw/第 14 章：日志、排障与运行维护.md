# 第 14 章：日志、排障与运行维护

> **这一章解决什么问题？**
> 到目前为止，你已经有了 Gateway、Agent、Sandbox、Cron、Importer——一整套自动化系统。系统在工作的时候一切看起来很美好，但总有一天你打开电脑，发现昨天的资讯没有抓取、汉字数据导入失败了、或者 Agent 返回的结果全是乱码。
> 这一章教你建立两种能力：**出了问题能快速定位根因**，以及**在问题发生之前就能看到预兆**。这就是"可观察性"——从"能跑"进化到"能维护"。

---

## 14.1 七种常见故障类型

在你长期运行 OpenClaw 的过程中，故障基本上落在以下七个类型里：

### 14.1.1 Gateway 起不来

**症状：** 运行 `openclaw gateway start` 后报错或立即退出。

**常见原因：**

| 原因 | 表现 | 检查方式 |
|------|------|----------|
| 端口被占用 | `Address already in use` | `lsof -i :端口号` |
| 配置文件语法错误 | `YAML parse error` | 检查 config 文件缩进 |
| 模型 API Key 过期 | 启动后无法响应 | `openclaw health` |
| 依赖服务未安装 | `command not found` | `openclaw doctor` |

### 14.1.2 Agent 不响应

**症状：** 运行 Agent 后长时间没有输出，或返回空结果。

**常见原因：**
- 模型 API 连接超时（网络问题）
- Prompt 过长导致上下文窗口溢出
- Agent 配置中指向了不存在的文件路径
- Agent 的 Workspace 权限设置不允许读取所需文件

### 14.1.3 Sandbox 失败

**症状：** Agent 需要 Sandbox 但容器无法启动、命令无法执行。

**常见原因：**
- Docker 未运行
- Docker 镜像未拉取
- 挂载路径不存在
- 容器内缺少必要工具（`curl`、`python` 等）

### 14.1.4 Cron 不触发

**症状：** 预定的定时任务到了时间但没有执行。

**常见原因：**
- Gateway 没有在运行（Cron 依赖于 Gateway 进程）
- Cron 表达式写错了（`0 8 * * *` 和 `* 8 * * *` 差距巨大）
- 系统时区与你预期的不一致
- 之前的任务还在运行，新任务被跳过

### 14.1.5 输出为空

**症状：** Agent 运行成功了（没有报错），但输出文件是空的或内容明显不完整。

**常见原因：**
- 数据源网站改版了，选择器已失效
- 模型能力不足以处理请求（换了一个便宜模型后质量下降）
- 输出路径配置错误，Agent 把结果写到了别的地方

### 14.1.6 权限不足

**症状：** 报错信息包含 `Permission denied`、`not allowed`、`approval required`。

**常见原因：**
- Agent 的安全配置限制了某个操作
- 文件系统权限不满足（容器内用户 vs 宿主机用户）
- 需要 Approval 的操作没有被批准

### 14.1.7 路径错误

**症状：** `File not found`、路径相关的报错。

**常见原因：**
- 绝对路径 vs 相对路径混用
- 容器内路径 vs 宿主机路径不一致
- Workspace 目录结构变更后 Agent 配置没有更新

## 14.2 五步排障路径

遇到问题时不要乱猜——按照这个路径一步步排查：

```
health → status → logs → doctor → config / workspace 边界
```

### 14.2.1 第一步：health

```bash
openclaw health
```

`health` 告诉你系统的基本健康状态：Gateway 是否在运行、模型连接是否正常、核心服务是否可用。

- 如果 `health` 报错 → 问题在基础设施层（Gateway / 网络 / 模型 API）
- 如果 `health` 正常 → 问题不在基础设施层，继续下一步

### 14.2.2 第二步：status

```bash
openclaw status
```

`status` 告诉你当前各个组件的运行状态：哪些 Agent 在运行、哪些 Cron 任务在调度、Sandbox 是否可用。

- 如果某个 Agent 状态异常 → 问题在 Agent 配置或执行层
- 如果 Cron 任务没有在调度列表中 → 问题在 Cron 注册层

### 14.2.3 第三步：logs

```bash
openclaw logs
openclaw logs --agent collector-jp-news
openclaw logs --tail 50
```

`logs` 是最详细的信息来源。它记录了每一次操作的输入、输出、错误信息。

**读日志的技巧：**
- 从最后的错误往上找——先找到 `ERROR` 或 `FAILED`，再往前看上下文
- 注意时间戳——确认错误发生的时间和你预期的触发时间是否一致
- 看堆栈信息的最底层——通常最底层的错误才是根因

### 14.2.4 第四步：doctor

```bash
openclaw doctor
```

`doctor` 进行一次全面检查：配置文件是否合法、依赖是否满足、路径是否存在、权限是否正确。它会给出具体的修复建议。

优先使用 `doctor`——它比你手动检查更全面、更快。

### 14.2.5 第五步：config 与 Workspace 边界

如果前四步没有定位到问题，需要手动检查：

- Agent 配置文件中路径是否正确
- Workspace 目录结构是否被意外修改
- Agent 的权限边界是否阻止了它需要执行的操作

## 14.3 如何建立可观察性

排障能力让你在问题发生后解决问题；可观察性让你在问题发生前（或发生时）就察觉到异常。

### 14.3.1 日志目录

为你的系统建立统一的日志目录结构：

```
workspace-root/
├── logs/
│   ├── gateway/          # Gateway 运行日志
│   ├── agents/           # 各 Agent 的执行日志
│   │   ├── collector-ai-news/
│   │   ├── collector-jp-news/
│   │   └── curator-kanji/
│   ├── cron/             # Cron 任务日志
│   └── importer/         # 导入任务日志
```

每个日志文件应该包含：
- 时间戳
- 操作类型（运行 / 检查 / 导入）
- 结果状态（成功 / 失败 / 部分成功）
- 关键数据量（处理了多少条记录）

### 14.3.2 任务输出目录

区分"日志"和"输出"——日志是记录过程，输出是任务的产物：

```
workspace-root/
├── output/
│   ├── daily/            # 每日产出
│   │   ├── 2025-01-15/
│   │   │   ├── ai-news.json
│   │   │   └── jp-edu-news.json
│   │   └── 2025-01-16/
│   ├── weekly/           # 每周产出
│   └── staging/          # 待验证的产出
```

按日期组织输出文件，这让你在排查"某一天的任务少了"时能快速定位。

### 14.3.3 错误记录

为每次失败保留足够的上下文信息：

```json
{
  "timestamp": "2025-01-16T08:00:00Z",
  "agent": "collector-ai-news",
  "task": "daily-collection",
  "error_type": "source_unavailable",
  "error_message": "HTTP 403 Forbidden from https://example.com/feed",
  "retry_count": 3,
  "last_success": "2025-01-15T08:00:00Z"
}
```

### 14.3.4 失败样本保留

当 Agent 的输出有问题时，不要直接删除——保留失败的样本用于分析：

```
workspace-root/
├── failed-samples/
│   ├── 2025-01-16_collector-ai-news_empty-output.json
│   └── 2025-01-16_curator-kanji_malformed.json
```

失败样本可以帮你判断是数据源的问题、模型的问题还是 Schema 定义的问题。

### 14.3.5 审计信息

记录谁（哪个 Agent）在什么时候（时间戳）做了什么操作（读 / 写 / 执行 / 网络请求）。这些信息在排查安全问题时非常有用——特别是当多个 Agent 共享同一个 Workspace 时。

## 14.4 定位问题属于哪一类

排障的关键在于快速判断问题的类别，然后去对应的地方找原因。不同类别的问题有不同的排查方向。

### 14.4.1 模型问题

**特征：** Agent 运行了但输出内容有问题——答非所问、格式不对、内容有幻觉。

**排查方向：**
- Prompt 是否清晰？模糊的 Prompt 导致模糊的输出
- 模型能力是否匹配任务？轻量模型无法处理复杂的多步推理
- 最近是否换过模型？不同模型对同一个 Prompt 的表现可能差异很大
- 输入数据是否变长了？可能超出了模型的上下文窗口

**验证方法：** 手动用同样的 Prompt 在模型 API playground 测试，看返回结果是否正常。

### 14.4.2 权限问题

**特征：** 错误信息包含 `denied`、`not allowed`、`forbidden`、`approval`。

**排查方向：**
- 是 OpenClaw 层的权限控制还是操作系统层的文件权限？
- Agent 的安全配置文件中是否缺少了需要的权限？
- 是否有需要 Approval 的操作被阻塞了？

**验证方法：** 临时给 Agent 更宽的权限测试——如果问题消失，就是权限配置的问题（记得测试完恢复限制）。

### 14.4.3 环境问题

**特征：** "昨天还好好的，今天突然不行了"。

**排查方向：**
- Docker 是否在运行？（`docker ps`）
- 网络是否通畅？（`curl` 外部 API 试试）
- 磁盘空间是否满了？（`df -h`）
- 系统是否更新了？（操作系统更新可能影响 Docker、路径等）

**验证方法：** `openclaw doctor` 通常能检测出环境问题。

### 14.4.4 数据源问题

**特征：** 输出为空或数据明显不完整，但系统没有报错。

**排查方向：**
- 目标网站是否改版了？
- API 是否更新了接口格式？
- 是否触发了反爬虫机制？（返回 403 或验证码页面）

**验证方法：** 手动访问数据源 URL，确认内容和格式是否变化。

### 14.4.5 配置问题

**特征：** 有一些组件正常、另一些不正常，或新添加的功能不工作。

**排查方向：**
- 配置文件的 YAML 缩进是否正确？
- 路径引用是否都是有效的？
- 修改配置后是否重启了 Gateway？

**验证方法：** `openclaw config validate` 或 `openclaw doctor` 验证配置文件语法。

### 14.4.6 问题分类速查表

| 症状 | 最可能的类别 | 首选排查工具 |
|------|------------|-------------|
| 完全无输出 | 环境 / 权限 | `health` → `doctor` |
| 有输出但内容错误 | 模型 / 数据源 | `logs` + 手动测试 |
| 间歇性失败 | 网络 / 数据源 / 资源限制 | `logs`（看失败时间模式） |
| 新配置不生效 | 配置 / 重启 | `config validate` |
| 昨天正常今天坏了 | 环境 / 数据源 | `doctor` + 手动访问 |
| 权限相关报错 | 权限 | 安全配置文件 |

## 14.5 日常维护习惯

### 14.5.1 每日快速检查

养成一个习惯——每天花 30 秒看一下系统状态：

```bash
openclaw health && openclaw status
```

如果两个命令都正常返回，今天的自动化任务大概率没问题。

### 14.5.2 每周检查

每周花 5 分钟做一次更深入的检查：

- 查看本周的日志有没有 ERROR 记录
- 查看输出目录的文件数量是否符合预期（比如每日一个文件，本周应该有 7 个）
- 检查磁盘空间使用情况
- 运行 `openclaw doctor` 做一次全面诊断

### 14.5.3 定期清理

日志和输出文件会不断增长。制定清理策略：

- 日志文件保留 30 天
- 成功的输出文件保留 90 天（或根据需要永久保留）
- 失败样本保留 14 天
- 保留清理脚本，不要手动删除

## 14.6 如果这里失败，先检查什么

**"openclaw health 显示正常但 Agent 还是不工作"**
→ `health` 只检查基础设施层。Agent 的问题可能在配置层——用 `openclaw doctor` 或手动检查 Agent 配置文件。

**"日志太多看不过来"**
→ 用 `--tail` 参数只看最后 N 行；用 `--agent` 参数只看特定 Agent 的日志；用 `grep` 过滤 `ERROR` 或 `FAILED` 关键字。

**"不确定问题归哪一类"**
→ 用排除法。先 `health` 排除基础设施，再 `doctor` 排除环境，再 `logs` 看具体错误——错误信息通常会明确指向类别。

**"修复了但不确定是否真的好了"**
→ 记住 Cron 那一章的幂等性概念——修复后手动触发一次任务，确认完整流程正常。

## 本章学完后你应该会什么

1. **能系统化地排查故障**——不再盲目试错，而是按照 health → status → logs → doctor → config 的路径逐步缩小范围。
2. **建立了可观察性体系**——日志目录、输出目录、错误记录、失败样本，让系统状态对你透明。
3. **能快速分类问题**——模型问题、权限问题、环境问题、数据源问题、配置问题，不同类别去不同地方找原因。
4. **有了日常维护节奏**——每日 30 秒快速检查 + 每周 5 分钟深度检查，防患于未然。
