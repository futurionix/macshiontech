# 第 8 章：Sandbox 学习专题

> **这一章解决什么问题？**

## 8.1 Docker Sandbox 基本原理

### 8.1.1 为什么 Agent 跑在容器里更安全

当 Agent 在你的主机上直接运行时，它拥有的能力和你当前用户的权限一致——如果它有执行权限，它可以运行任何你能运行的命令；如果它有写权限，它可以写你能写的任何文件。**这意味着一个失控的 Agent 可以造成的损害范围 = 你的用户权限范围。**

Docker 容器改变了这个等式。容器是一个隔离的运行环境：

- **文件系统隔离**：容器内有自己的文件系统。Agent 在容器内写的文件默认不会影响宿主机，除非你显式地做了目录挂载。
- **进程隔离**：容器内的进程看不到宿主机上的其他进程。Agent 无法干扰宿主机上运行的其他程序。
- **网络隔离**：容器可以配置独立的网络策略。你可以限制容器只能访问特定的域名或 IP。
- **资源隔离**：可以限制容器的 CPU、内存使用，防止 Agent 消耗过多系统资源。

**一个直观的类比：** 在主机上运行 Agent 就像让助手在你的办公室里自由走动。在容器里运行 Agent 就像让助手在一个单独的房间里工作——他只能通过你开的窗口（目录挂载）来拿资料和交付成果。

### 8.1.2 容器不是绝对安全

容器隔离不是银弹。你需要理解它的局限：

**容器逃逸**：虽然罕见，但存在已知的容器逃逸漏洞。保持 Docker 版本更新可以降低这个风险，但不能完全消除。

**挂载穿透**：如果你把宿主机的敏感目录（如 `~/.ssh/`、`~/.aws/`）挂载到了容器内，容器里的 Agent 就能读取这些敏感文件——隔离形同虚设。

**网络未限制**：如果你没有限制容器的网络策略，容器内的 Agent 仍然可以自由访问互联网——可以把数据发送到任何外部服务。

**权限配置错误**：如果以 root 用户运行容器、或者给了容器 `--privileged` 标志，容器的隔离保护会大幅削弱。

### 8.1.3 容器更像损害控制手段

对 Sandbox 的正确理解是：**它不是"绝对安全"的保证，而是"损害控制"的手段。** 它的作用是把出问题时的影响范围从"你的整个系统"缩小到"一个可以随时销毁的容器"。

- 没有 Sandbox：Agent 执行了 `rm -rf /important-data` → 你的重要数据被删
- 有 Sandbox：Agent 在容器内执行了 `rm -rf /` → 容器的文件系统被清、宿主机不受影响，销毁容器即可

OpenClaw 官方文档也明确将 Sandbox 功能绑定到 Docker，把它定位为"安全运行 Agent 的基础设施"而不是"安全的保证"。

## 8.2 哪些 Agent 必须放进 Sandbox

### 8.2.1 必须使用 Sandbox 的场景

**采集员（Collector）**

采集员需要访问互联网来抓取数据。网络访问是高风险权限——Agent 可能连接到意料之外的 URL、下载不明内容、甚至被恶意网站注入 payload。把采集员放在 Sandbox 中，即使它下载了恶意内容，影响范围也限制在容器内。

**原型员（Prototyper）**

原型员需要执行权限——运行代码、安装依赖包、启动 preview 服务器。执行权限是最危险的权限之一（回忆第 3 章）。必须放在 Sandbox 中。

**带 Shell 权限的整理员**

如果你的整理员需要运行数据处理脚本（比如用 Python 脚本做字段清洗），那它就需要执行权限，也应该放在 Sandbox 中。

### 8.2.2 判断标准

使用以下决策树判断一个 Agent 是否需要 Sandbox：

```
Agent 需要执行 Shell 命令吗？
├── 是 → 必须 Sandbox
└── 否 → Agent 需要访问互联网吗？
         ├── 是 → 推荐 Sandbox
         └── 否 → Agent 有写权限吗？
                  ├── 是 → 可选 Sandbox（低风险可不用）
                  └── 否 → 不需要 Sandbox
```

## 8.3 哪些场景可以先不进 Sandbox

### 8.3.1 低风险只读总结

如果 Agent 只是读取本地文件并生成总结（不访问网络、不执行命令），风险很低。例如：

- 读取 validated 目录中的 JSON 文件，生成统计摘要
- 读取 Markdown 课程草稿，生成结构大纲

这类任务不需要 Sandbox。

### 8.3.2 临时本地实验

在学习阶段，你可能会频繁地做临时实验——"让 Agent 帮我总结一下这个文件的内容"之类的简单任务。如果每次都配置 Sandbox，会极大降低实验效率。

**建议：** 临时实验如果不涉及执行权限和网络访问，可以不用 Sandbox。但要确保 Agent 的写权限被限制在实验目录内。

### 8.3.3 完全受控目录内的小任务

如果一个 Agent 只在一个你专门创建的小目录内工作——该目录里没有重要数据、即使被完全清空也无所谓——那么 Sandbox 的增益不大。

**判断依据：** "如果这个目录里的所有文件都被删除了，我会心疼吗？" 如果答案是"不会"，那不用 Sandbox 也行。

## 8.4 Sandbox 的局限与常见坑

### 8.4.1 文件挂载

容器默认有自己独立的文件系统。如果 Agent 需要读取宿主机上的配置文件、或者把产出写回宿主机，你需要配置目录挂载。

**常见坑一：挂载路径不存在。** 你配置了把 `/workspace/kanji-staging/staging/` 挂载到容器内的 `/data/staging/`，但如果宿主机上的 `/workspace/kanji-staging/staging/` 目录不存在，Docker 会自动创建一个空目录（或者报错，取决于 Docker 版本和配置）。Agent 运行后看到的是空目录，产出也不会写到你期望的位置。

**解决方法：** 在启动 Sandbox 之前，确认挂载源目录已经存在。

**常见坑二：权限不匹配。** 容器内的用户 ID 和宿主机的用户 ID 可能不同。Agent 在容器内以 UID 1000 写入文件，但宿主机上你的用户是 UID 501——你可能无法读取容器产出的文件，或者容器内的 Agent 无法读取你在宿主机上创建的文件。

**解决方法：** 配置容器的运行用户 ID 与宿主机一致，或者设置合适的文件权限。

**常见坑三：挂载了不该挂载的目录。** 为了"方便"，把宿主机的 home 目录整个挂载到容器内——这基本上废掉了文件系统隔离。你的 `.ssh/`、`.aws/`、`.gitconfig` 等敏感文件全暴露了。

**原则：** 只挂载 Agent 工作所需的最小目录集。用到什么挂什么，不要图方便一挂了之。

### 8.4.2 网络连通

容器的网络配置决定了 Agent 能访问哪些外部资源。

**默认情况：** 容器通常默认可以访问互联网。这意味着仅仅把 Agent 放进容器不会自动限制它的网络访问——你需要额外配置网络策略。

**理想做法：** 如果可能的话，限制容器只能访问特定的域名或 IP 白名单。比如采集员只需要访问 RSS 源的域名，不需要访问其他任何地址。

**常见坑：** DNS 解析失败。容器的 DNS 配置和宿主机可能不同。如果 Agent 报错说"无法解析域名"，检查容器的 DNS 配置。

### 8.4.3 环境变量

Agent 可能需要环境变量——比如 API Key、模型地址等。这些环境变量需要从宿主机传递到容器内。

**常见坑：** 环境变量忘记传递。Agent 在容器内运行时读不到 API Key，连接模型失败。

**解决方法：** 在 Sandbox 配置中明确声明需要传递的环境变量列表。不要用 `--env-file` 传递整个 env 文件——只传递 Agent 需要的变量，遵循最小权限原则。

### 8.4.4 容器持久化

默认情况下，容器销毁后其内部文件系统的所有数据都会丢失。如果 Agent 的产出没有写到挂载目录，而是写到了容器内部的路径——容器销毁后产出就丢了。

**常见坑：** Agent 把结果写到了 `/tmp/output.json`（容器内部路径），而不是你挂载的 `/data/staging/output.json`。容器结束后，`/tmp/output.json` 消失。

**解决方法：** 在 Agent 的配置中明确指定输出路径为挂载目录内的路径。运行后检查挂载目录确认产出文件存在。

### 8.4.5 宿主机差异

Docker 在不同操作系统上的行为有差异：

- **macOS**：Docker Desktop 通过虚拟化层运行，文件挂载性能比 Linux 差。大量小文件的读写可能明显变慢。
- **Linux**：原生运行，性能最好，但用户权限映射可能需要额外处理。
- **Windows（WSL2）**：需要关注 WSL2 和 Windows 文件系统之间的路径转换问题。

OpenClaw 的官方 issue 和文档都提到了 Docker/Sandbox 组合在不同环境下可能遇到的实际问题。遇到环境相关的错误时，优先查阅官方文档的 troubleshooting 部分。

## 8.5 你的 Sandbox 学习目标

### 8.5.1 知道何时用

回到 8.2 节的决策树。你应该能快速判断一个 Agent 是否需要 Sandbox：

- 需要执行 Shell 命令 → 必须
- 需要访问网络 → 推荐
- 只读本地文件 → 不需要

### 8.5.2 知道为什么用

不是"因为文档说要用"，而是你能清楚地说出："这个 Agent 有执行权限，如果它生成了一条危险的 Shell 命令，在 Sandbox 里最多毁掉一个容器，在主机上可能毁掉我的整个工作环境。所以我要用 Sandbox。"

### 8.5.3 知道怎么排查

当 Sandbox 相关的问题出现时，按以下路径排查：

```
1. Docker 是否安装并运行？
   → docker --version && docker info

2. 容器是否成功启动？
   → 检查 OpenClaw 日志中的容器启动记录

3. 挂载目录是否正确？
   → 检查容器配置中的 volume mapping
   → 进入容器检查挂载点是否有预期文件

4. 网络是否连通？
   → 在容器内 ping 外部域名
   → 检查 DNS 配置

5. 环境变量是否传递？
   → 在容器内 echo 环境变量确认

6. 产出文件是否在挂载目录？
   → 检查 Agent 的实际输出路径
```

### 8.5.4 知道怎么验证隔离是否生效

**验证文件系统隔离：**

在容器内创建一个测试文件（比如 `/tmp/sandbox-test.txt`），然后在宿主机上确认这个文件不存在。这证明容器的文件系统确实是隔离的。

**验证挂载生效：**

在挂载目录内创建一个测试文件，确认容器内可以读到。在容器内向挂载目录写入一个文件，确认宿主机上可以看到。

**验证进程隔离：**

在容器内运行 `ps aux`，确认看不到宿主机上的进程。

## 8.6 如果这里失败，先检查什么

**"Docker 命令报错 'Cannot connect to the Docker daemon'"**
→ Docker Desktop 没有启动。在 macOS 上打开 Docker Desktop 应用；在 Linux 上运行 `sudo systemctl start docker`。

**"容器启动了但 Agent 报错说找不到文件"**
→ 检查目录挂载配置。确认（1）宿主机路径存在，（2）容器内路径正确，（3）文件权限允许读取。

**"Agent 在 Sandbox 内运行非常慢"**
→ 在 macOS 上，Docker 的文件 I/O 受虚拟化层影响可能较慢。如果可能，减少挂载目录中的文件数量，或者使用 Docker 的 cached/delegated 挂载选项。

**"我不确定 Docker 装没装 / 版本够不够"**
→ 运行 `docker --version`。如果没有返回版本号，先安装 Docker。OpenClaw 文档应该有最低 Docker 版本要求——确认你的版本满足。

1. **能判断一个 Agent 是否需要 Sandbox**——基于权限（执行、网络）做决策，而不是盲目地"全放进去"或"全不放"。
