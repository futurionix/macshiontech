# 第 13 章：项目原型验证与开发协作

> **这一章解决什么问题？**
> 你已经有了数据（采集、整理、入库），现在想把它变成一个可以看到、可以交互的产品原型——搜索页面、展示页面、管理后台。Agent 可以帮你快速生成代码骨架、mock 数据、甚至基本的 UI。
> 但 Agent 在开发中的角色有清晰的边界。这一章教你两件事：**Agent 能帮你快速做到什么**，以及**哪些开发决策绝对不能交给 Agent**。
> 学完后你能用 Agent 快速验证产品创意，同时避免在关键决策上犯错。

---

## 13.1 Agent 在开发中的角色

### 13.1.1 能做的事

**需求整理**

你有一个模糊的想法："我想做一个汉字检定的搜索页面"。Agent 可以帮你把这个想法结构化：

- 页面应该有哪些功能？（搜索框、结果列表、详情页）
- 输入是什么？（汉字、读音、级别）
- 输出是什么？（匹配的汉字卡片列表）
- 需要对接哪些数据？（kanji 数据库表）

Agent 不是在替你做产品决策——它是在帮你把决策需要考虑的维度列出来，让你做更有信息量的判断。

**页面骨架生成**

给 Agent 一个功能描述，它可以生成前端页面的基础代码骨架：

```
"生成一个汉字搜索页面的 React 组件骨架：
- 顶部有一个搜索框，支持按汉字和读音搜索
- 搜索框下方显示级别筛选器
- 结果区域显示匹配的汉字卡片列表
- 每个卡片显示：汉字、级别、音读、训读"
```

Agent 生成的代码是一个起点，不是最终版本。你需要审查代码结构、补充业务逻辑、调整样式。

**数据 Mock**

在后端 API 还没有开发之前，Agent 可以根据你的 Schema 生成 mock 数据：

```json
[
  {"kanji": "鬱", "level": "1級", "on_reading": ["ウツ"], "kun_reading": ["ふさ.ぐ"]},
  {"kanji": "薔", "level": "1級", "on_reading": ["ショウ", "ビ"], "kun_reading": ["ばら"]},
  {"kanji": "麒", "level": "1級", "on_reading": ["キ"], "kun_reading": []}
]
```

这让你可以在没有真实数据的情况下就开始做前端开发和 UI 验证。

**测试用例草稿**

Agent 可以根据功能描述生成基础的测试用例：

```
- 搜索空字符串应该返回空结果
- 搜索一个已知汉字应该返回包含该汉字的结果
- 按级别筛选应该只返回对应级别的汉字
- 搜索一个不存在的汉字应该显示"未找到"提示
```

**PR 描述草稿**

如果你用 Git 管理代码，Agent 可以帮你写 Pull Request 的描述：

```markdown
## 变更摘要
新增汉字检定搜索页面组件

## 变更内容
- 添加 SearchPage 组件，支持按汉字和读音搜索
- 添加 LevelFilter 组件，支持按级别筛选
- 添加 KanjiCard 组件，展示汉字详情
- 添加 mock 数据用于开发测试

## 测试方式
运行 `npm run dev` 后访问 /search 页面
```

### 13.1.2 Agent 做这些事的价值

Agent 的价值不是"替你写代码"（它写的代码往往需要大量修改），而是**加速从 0 到 0.1 的过程**。有了骨架代码、mock 数据和测试用例草稿，你可以更快地进入"真正的开发"阶段——在已有的基础上修改和完善，而不是从空白文件开始。

## 13.2 不该交给 Agent 的开发决策

### 13.2.1 核心架构

"这个项目用什么技术栈？前后端分离还是 SSR？用什么框架？数据库选什么？"

这些决策影响项目的长期维护成本和扩展能力。Agent 可能给你一个看起来合理的建议，但它不了解你的团队能力、部署环境、长期规划。架构决策必须由你（或有经验的开发者）来做。

### 13.2.2 安全设计

"用户认证怎么做？API 权限怎么控制？敏感数据怎么加密？"

Agent 可能生成看起来正确的认证代码，但其中可能有微妙的安全漏洞。安全设计需要对攻击面、威胁模型有深入理解——这不是 Agent 的强项。

### 13.2.3 生产环境部署

"Docker 镜像怎么构建？CI/CD 流水线怎么配？域名和 SSL 证书怎么管理？"

部署涉及基础设施安全和线上稳定性。错误的部署配置可能导致数据泄露或服务中断。这些操作应该由理解生产环境风险的人来执行。

### 13.2.4 数据库最终建模

"表应该怎么设计？索引加在哪里？外键关系怎么建？"

Agent 可以生成 Schema 草案，但最终的数据库设计需要考虑查询模式、数据增长预测、性能优化——这些都需要你的领域知识和工程判断。

**核心原则：** Agent 做原型和草稿，人做架构和安全决策。

## 13.3 你的原型验证流程

### 13.3.1 六步 PoC 流程

```
想法描述 → UI/功能拆解 → 低保真原型 → 前端 demo → 人工审查 → 再决定是否正式开发
```

**第一步：想法描述**

用一段话描述你想做什么。不需要很详细——"我想做一个汉字检定搜索工具，让我能快速查某个汉字的级别和读音"就够了。

**第二步：UI/功能拆解**

把想法拆成具体的页面和功能点。Agent 可以协助这一步：

```
页面 1：搜索页
- 搜索框（支持汉字输入和读音输入）
- 级别筛选（下拉选择）
- 结果列表（卡片形式）

页面 2：详情页
- 汉字大字展示
- 读音列表（音读 + 训读）
- 常见词组
- 例句
```

**第三步：低保真原型**

用最简单的方式画出页面布局。可以用纸笔、可以用 Figma、也可以让 Agent 用 ASCII 画一个：

```
┌──────────────────────────────┐
│  [搜索框: 输入汉字或读音]      │
│  级别: [全部 ▼]               │
├──────────────────────────────┤
│  ┌────┐  ┌────┐  ┌────┐     │
│  │ 鬱  │  │ 薔  │  │ 麒  │     │
│  │1級  │  │1級  │  │1級  │     │
│  │ウツ │  │ショウ│  │ キ  │     │
│  └────┘  └────┘  └────┘     │
└──────────────────────────────┘
```

**第四步：前端 Demo**

让 Agent 基于低保真原型生成前端代码。使用 Agent 时的注意事项：

- 明确技术栈（"用 React + TypeScript"）
- 提供 mock 数据的格式
- 要求生成可直接运行的代码（不要有编译错误）

**第五步：人工审查**

运行 demo，自己用一下。问自己：

- 功能是否满足需求？
- 交互是否合理？
- 还缺什么功能？

这一步可能会让你修改需求、调整设计、然后回到第二步重新拆解。这是正常的——PoC 的价值就在于"尽早发现问题"。

**第六步：决策**

基于 PoC 的结果决定：

- 值得正式开发 → 开始写正式代码（不是在 PoC 代码上修改，而是重新设计架构后写）
- 需要调整方向 → 修改需求后重新做 PoC
- 放弃这个想法 → 把 PoC 记录存档，以后可能会用到

## 13.4 为什么原型员要隔离

### 13.4.1 它会读写代码

原型员 Agent 需要创建文件、写代码。这意味着它有文件写入权限。如果它不小心覆盖了你的重要代码文件——那就不是一个愉快的实验了。

### 13.4.2 可能会执行命令

生成的代码可能需要运行才能验证——`npm install`、`npm run dev`、`python app.py` 等。这些操作需要 Shell 执行权限。

### 13.4.3 可能会装依赖

运行代码前可能需要安装依赖包。Agent 可能执行 `npm install some-package` 或 `pip install some-lib`——这些安装操作可能引入有漏洞的包。

### 13.4.4 所以更应在 Sandbox / Workspace 内运行

把原型员放在 Sandbox 中运行——即使它安装了有问题的依赖包、执行了错误的命令，影响范围也限制在容器内。

同时确保原型员的 Workspace 是 `prototype-lab`，与你的正式代码仓库完全隔离。

## 13.5 适合你的 PoC 项目

### 13.5.1 汉字检定搜索页

**目标：** 一个简单的网页，可以搜索汉字并查看详情。

**技术方案：**
- 前端：React（或者更简单的纯 HTML + JS）
- 数据：mock JSON 文件（后续对接真实数据库）
- 功能：搜索、筛选、详情展示

**Agent 能做的：**
- 生成页面组件代码
- 生成 mock 数据
- 生成基础 CSS 样式

**你需要做的：**
- 确认功能需求
- 审查代码质量
- 调整 UI 细节
- 决定是否值得正式开发

### 13.5.2 详情页

**目标：** 展示单个汉字的完整信息——读音、词组、例句、级别。

**关键设计决策：**
- 页面布局（汉字居中大字、信息分区展示）
- 交互方式（点击词组跳转到该词组的相关汉字？）
- 数据加载方式（预加载全量 vs 按需查询）

### 13.5.3 学习模块页

**目标：** 展示一个课程模块的内容——Lesson 列表、每个 Lesson 的汉字卡片、练习题。

**数据来源：** 第 11 章整理的课程模块 Markdown / JSON 文件。

### 13.5.4 资讯摘要后台

**目标：** 展示每日抓取的资讯摘要，支持按日期浏览。

**数据来源：** 第 9 章 cron 产出的 daily JSON 文件。

## 13.6 如果这里失败，先检查什么

**"Agent 生成的代码跑不起来"**
→ 检查 Agent 使用的依赖版本。Agent 可能使用了过时的 API 或未安装的库。告诉 Agent 你的具体版本约束（"我用的是 React 18"）。

**"生成的代码和我预期的完全不一样"**
→ 你的需求描述可能不够具体。提供更详细的功能描述、UI 草图、数据格式示例。Agent 不会猜你的偏好——你需要明确地告诉它。

**"PoC 跑起来了但不知道下一步该做什么"**
→ 回到第六步的决策框架：功能满足需求吗？交互合理吗？值得正式开发吗？如果答案都是"是"，下一步是重新设计架构后写正式代码——不要在 PoC 代码上继续堆功能。

**"不确定技术栈选什么"**
→ 选你最熟悉的。PoC 的目的是快速验证想法，不是学习新技术。如果你熟悉 React 就用 React，熟悉 Vue 就用 Vue，什么都不熟悉就用纯 HTML + JavaScript。

## 本章学完后你应该会什么

1. **能用 Agent 快速生成产品原型**——从想法到可运行的 demo，借助 Agent 加速 0 到 0.1 的过程。
2. **清楚了 Agent 在开发中的角色边界**——做原型和草稿，不做架构和安全决策。
3. **有了 PoC 验证的系统流程**——不是随意让 Agent 写代码，而是有明确的步骤和决策点。
4. **知道了为什么原型员必须隔离**——执行权限 + 依赖安装 = 必须 Sandbox。
