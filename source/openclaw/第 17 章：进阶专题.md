## 17.1 Channels / Message / Directory

### 17.1.1 这是什么

到目前为止，你的 Agent 是孤立的：collector 采集数据、curator 整理数据、importer 导入数据——它们之间通过文件系统传递信息（collector 写入 staging，curator 从 staging 读取）。

Channels 和 Message 提供了一种更正式的 Agent 间通信机制：

- **Channel**：一个命名的消息通道，Agent 可以向通道发送消息或从通道接收消息
- **Message**：结构化的数据单元，包含发送者、接收者、内容、时间戳等元信息
- **Directory**：Agent 的注册表，让 Agent 可以发现其他 Agent 的存在和能力

### 17.1.2 解决什么问题

文件系统传递信息有几个局限：

- 没有通知机制——curator 不知道 collector 什么时候写完了，只能轮询检查
- 没有状态跟踪——你不知道某个文件是否已经被处理过
- 没有错误传播——collector 失败了，curator 不知道

Channels 解决这些问题：collector 完成后发一条消息到 channel，curator 收到消息后开始工作；如果 collector 失败了，它可以发一条失败消息，curator 会进入等待而不是处理空数据。

### 17.1.3 什么时候需要学

**当你有 3 个以上 Agent 需要协作时。** 如果只有 collector → curator 两步流程，文件系统完全够用。当流程变成 collector → curator → validator → importer 四步链路时，用 channel 来协调会比文件轮询更可靠。

## 17.2 Plugins / Hooks / Browser 深度使用

### 17.2.1 Plugins

Plugin 是可复用的功能组件——它比 Skill 更重量级，通常包含完整的业务逻辑。

你可以把"采集某类网站"的逻辑封装成 Plugin，让不同的 Agent 复用。比如一个"RSS Feed 解析 Plugin"，collector-ai-news 和 collector-jp-news 都可以使用它。

### 17.2.2 Hooks

Hook 是事件钩子——在特定事件发生时自动触发的脚本或逻辑。

常见的 Hook 点：

| Hook | 触发时机 | 用途示例 |
|------|---------|---------|
| before-agent-run | Agent 执行前 | 检查前置条件是否满足 |
| after-agent-run | Agent 执行后 | 自动归档输出、发送通知 |
| on-agent-error | Agent 执行出错时 | 自动重试或告警 |
| before-cron-trigger | Cron 任务触发前 | 检查资源是否就绪 |

### 17.2.3 Browser 深度使用

第 10 章提到了 Agent 采集网页数据，但那是基础用法。Browser 功能的深度使用包括：

- **动态页面抓取**：处理需要 JavaScript 渲染的页面
- **表单交互**：自动填写表单、点击按钮
- **多步导航**：先登录 → 再导航到目标页面 → 最后提取数据
- **截图和 PDF**：对页面进行截图或导出 PDF

### 17.2.4 什么时候需要学

- **Plugins**：当你发现多个 Agent 在重复相同的逻辑时
- **Hooks**：当你需要在 Agent 执行前后自动做一些事情时（通知、检查、归档）
- **Browser 深度使用**：当你需要采集的数据源需要 JavaScript 渲染或登录时

## 17.3 Nodes / 分布式执行

### 17.3.1 这是什么

到目前为止，你所有的 Agent 都在一台机器上运行。Nodes 功能允许你把工作负载分散到多台机器上。

### 17.3.2 解决什么问题

- **性能瓶颈**：当你有大量采集任务时，单台机器的 CPU、网络、内存可能成为瓶颈
- **地理分布**：你可能需要从不同地区的网络采集数据（避免某些网站的地区限制）
- **资源隔离**：把 CPU 密集型任务（数据处理）和 I/O 密集型任务（网络采集）分到不同机器

### 17.3.3 什么时候需要学

**当单台机器已经无法满足你的负载需求时。** 对于个人使用场景（每日几十次采集任务），单台机器通常足够。当你的任务数量增长到每日数百次、或者遇到明确的性能瓶颈时，再考虑分布式。

## 17.4 Multi-Host / Remote Gateway

### 17.4.1 这是什么

第 15 章提到了"高风险任务单独 Gateway"。Multi-Host 和 Remote Gateway 是这个概念的技术实现——你可以在不同的主机上运行不同的 Gateway 实例，并且从一台机器远程管理另一台机器上的 Gateway。

### 17.4.2 解决什么问题

- **安全隔离**：高风险操作和低风险操作物理分离
- **灵活部署**：Gateway 运行在云服务器上，你从笔记本电脑远程管理
- **团队使用**：不同团队成员使用不同的 Gateway 实例

### 17.4.3 架构示意

```
你的笔记本电脑
  └── 远程管理 ──→ 云服务器 A（低风险 Gateway）
                     ├── collector-ai-news
                     └── collector-jp-news
  └── 远程管理 ──→ 云服务器 B（高风险 Gateway）
                     ├── importer-kanji
                     └── prototyper
```

### 17.4.4 什么时候需要学

**当你需要 7x24 运行自动化任务时。** 如果你的 Cron 任务需要在你关掉电脑后继续运行，把 Gateway 部署到一台始终在线的服务器上是自然的下一步。

## 17.5 团队协作 / 共享操作

### 17.5.1 这是什么

到目前为止，整个 OpenClaw 系统都是你一个人在使用——你设计 Agent、配置权限、管理 Workspace。团队协作功能让多个人共同使用同一套系统。

### 17.5.2 涉及的问题

团队使用引入了新的复杂性：

- **权限管理**：谁可以创建 Agent？谁可以修改配置？谁可以批准高风险操作？
- **资源隔离**：不同成员的 Agent 和数据应该如何隔离？
- **审计追溯**：出了问题时能追溯到是谁的 Agent 做了什么操作

### 17.5.3 什么时候需要学

**当你需要和其他人一起使用 OpenClaw 时。** 对于个人学习和个人项目，完全不需要团队协作功能。当你把 OpenClaw 引入团队工作流——多人共同维护 Agent、共同使用采集数据——时再学习。

## 17.6 进阶功能学习路线建议

不要一次学完所有进阶功能。根据你的实际需求，按这个优先级来：

| 优先级 | 功能 | 触发条件 | 预期学习时间 |
|--------|------|---------|-------------|
| 1 | Hooks | 你需要 Agent 执行后自动通知或归档 | 1-2 小时 |
| 2 | Plugins | 你发现多个 Agent 重复了相同的逻辑 | 半天 |
| 3 | Browser 深度 | 你需要采集需要 JS 渲染的网站 | 半天 |
| 4 | Channels | 你有 3+ Agent 组成链式流程 | 1 天 |
| 5 | Remote Gateway | 你需要 7x24 运行任务 | 1 天 |
| 6 | Nodes / 分布式 | 你遇到了单机性能瓶颈 | 1-2 天 |
| 7 | 团队协作 | 你需要和其他人共用系统 | 1-2 天 |
