# 第 9 章：Cron 与自动化专题

> **这一章解决什么问题？**
> 到目前为止，你所有的 Agent 任务都是手动触发的——你在终端里敲一条命令，Agent 执行一次。这在学习阶段没问题，但如果你想让系统真正为你工作——"每天早上自动抓取 AI 编程动态"、"每周自动汇总汉字学习进展"——你需要**定时任务**。
> 这一章教你：什么样的任务适合 cron 化、怎么设计一个可靠的定时任务、以及当定时任务出问题时怎么排查。学完后你能让 OpenClaw 从"你在的时候干活"变成"你不在的时候也干活"。

---

## 9.1 定时任务思维

### 9.1.1 任务触发条件

手动运行和定时运行的本质区别在于**触发条件**：

- **手动触发**：你决定"现在该跑了"→ 执行
- **定时触发**：系统到了设定的时间 → 自动执行

定时触发看起来只是把人工操作换成了自动操作，但它带来了一系列新问题，你在设计手动任务时不会遇到：

### 9.1.2 时间维度

定时任务需要回答一个关键问题：多久跑一次？

| 频率 | 示例 | 适合的任务类型 |
|:---|:---|:---|
| 每小时 | 整点执行 | 高频率监控、实时性要求高的巡检 |
| 每天 | 每天 08:00 | 日报生成、每日资讯抓取 |
| 每周 | 每周一 09:00 | 周报汇总、低频数据更新 |
| 每月 | 每月 1 日 | 月度统计、账单（如 API 成本） |

**常见误区：频率设太高。** "我想实时掌握最新动态，所以每 5 分钟跑一次抓取。" 这会导致：（1）API 调用费用快速增长，（2）数据源可能因为你访问过频繁而封禁你，（3）产出大量重复内容。大部分巡检任务，每天一次就够了。

### 9.1.3 重复执行

手动任务通常只执行一次。定时任务会反复执行——每天一次意味着一年 365 次。这个差异带来了一个核心问题：**每次执行的结果之间是什么关系？**

- 每次生成独立的产出文件（如 `daily-2025-01-15.json`、`daily-2025-01-16.json`）→ 产出会越来越多，需要清理策略
- 每次覆盖同一个文件（如 `latest.json`）→ 丢失了历史记录
- 每次追加到同一个文件 → 文件会越来越大

**建议：** 每次生成带日期的独立文件。定期清理超过保留期的旧文件（比如只保留最近 30 天的日报）。

### 9.1.4 幂等性

幂等性（Idempotency）是定时任务设计中最重要的概念之一：**同一个任务在相同条件下执行多次，结果应该和执行一次相同。**

为什么幂等性对定时任务如此重要？因为定时任务可能因为各种原因被执行多次：

- 系统重启后 cron 调度器重新启动，可能重新触发已执行的任务
- 你手动重跑了一次失败的任务
- 调度器的时间出了偏差

如果任务是幂等的，重复执行不会造成问题。如果不是——比如"每次执行都向数据库插入一条记录、不检查重复"——重复执行就会产生重复数据。

**实现幂等性的常用方法：**

- 基于日期命名输出文件（`daily-2025-01-15.json`），同一天重跑只是覆盖同一天的文件
- 在写入前检查是否已存在相同记录（去重）
- 使用 upsert（存在则更新，不存在则插入）而不是纯 insert

### 9.1.5 失败重试

定时任务不可避免地会失败：网络中断、数据源临时不可用、模型 API 超时。关键问题是：**失败后怎么办？**

- **不重试**：记录失败日志，等下一次定时触发时自然重跑。适合对时效性要求不高的任务。
- **自动重试 N 次**：失败后间隔一段时间重试，最多重试 N 次。适合因临时故障导致失败的场景。
- **告警 + 人工介入**：失败后发出告警（日志、通知），由你来判断是否需要手动处理。

**学习阶段建议：** 不重试。让失败自然暴露在日志中。你需要先看到"是什么原因导致了失败"，而不是让自动重试掩盖了问题。

## 9.2 OpenClaw Cron 能做什么

### 9.2.1 每日资讯巡检

最典型的 cron 任务：每天固定时间抓取信息源，生成当日摘要。

```
任务：每天 08:00 抓取 AI 编程动态
Agent：news-watcher
输入：config/sources.json（RSS 源列表）
输出：staging/daily-{date}.json
频率：每天一次
```

### 9.2.2 定期数据抓取

对于需要持续积累的数据（比如汉字检定资料），可以设置定期抓取：

```
任务：每周一抓取新发布的检定参考资料
Agent：kanji-collector
输入：config/sources.json
输出：staging/weekly-{date}.json
频率：每周一次
```

注意：大规模数据抓取不适合高频率 cron，因为（1）数据源更新没那么快，（2）高频抓取可能被封禁。

### 9.2.3 定时生成摘要

如果你已经积累了一段时间的日报数据，可以定时生成周报或月度汇总：

```
任务：每周日生成本周 AI 编程动态周报
Agent：news-summarizer（或 news-watcher 的 summarize 模式）
输入：staging/daily-*.json（本周的日报文件）
输出：reports/weekly-{date}.md
频率：每周一次
```

### 9.2.4 周期性检查变更

有些信息不是"要去抓取"，而是"要去检测有没有变化"：

```
任务：每天检查 AWS 认证考试官网是否有新的考试大纲更新
Agent：change-detector
输入：config/watch-urls.json + cache/previous-snapshots/
输出：reports/changes-{date}.json（如果有变化）
频率：每天一次
```

OpenClaw 的 Cron 官方文档就是按 scheduler-job 模式来组织这些能力的——定义触发时间、关联 Agent、指定输入输出。

## 9.3 不适合直接 Cron 化的任务

### 9.3.1 高成本抓取

如果一次抓取会消耗大量 API Token（比如需要 GPT-4 处理上百篇文章的深度分析），不应该随意 cron 化。先手动跑几次评估成本，确认在预算范围内后再设为定时任务。

### 9.3.2 高风险写入

任何涉及"写入正式数据库"、"发布到外部平台"、"修改生产配置"的操作，都不应该无人值守地 cron 化。这些操作应该保持手动触发，或者加上人工审批（Approvals）环节。

### 9.3.3 需要登录态的复杂交互

有些数据源需要登录后才能访问。登录态（Session / Cookie / Token）经常过期。如果 cron 任务依赖登录态，它会频繁因为"登录过期"而失败，维护成本很高。

**替代方案：** 如果可能，使用该服务提供的 API 和 API Key 来访问，而不是模拟浏览器登录。API 方式更稳定、更适合自动化。

### 9.3.4 不可逆操作

任何执行后无法回滚的操作——删除文件、清空表、发送邮件——都不应该放在无人值守的 cron 中。

## 9.4 设计一个好的 Cron Job

### 9.4.1 输入来源

Cron Job 的输入必须是确定性的。不能是"让 Agent 自己决定去哪里找数据"，而是"明确地指向一个配置文件或数据目录"。

```
✗ 不好的设计：Agent 每次自己搜索一遍数据源
✓ 好的设计：Agent 读取 config/sources.json 中预定义的源列表
```

### 9.4.2 去重逻辑

定时任务每次运行时，数据源中可能有一部分内容和上次执行时一样（比如 RSS 中昨天已经出现的文章还在）。Agent 需要有去重机制：

- 基于 URL 去重（同一个 URL 不重复处理）
- 基于时间戳去重（只处理比上次执行时间更新的内容）
- 基于内容哈希去重（同样的内容不重复处理）

**最简单的去重方法：** 每次把已处理的 URL 列表保存下来，下次执行时先加载这个列表，跳过已处理的。

### 9.4.3 输出路径

输出路径应该包含时间标识，让你能清楚地知道"这个文件是哪次任务产出的"：

```
✗ 不好的路径：staging/output.json（每次覆盖，无法追溯）
✓ 好的路径：staging/daily-2025-01-15.json（每次独立，可追溯）
```

### 9.4.4 失败告警

Cron 任务的一个重要特征是"无人值守"——你不会每天盯着它跑。所以你需要一种方式知道"它今天跑失败了"。

**最简单的告警方式：**

- 任务结束后写入一个 status 文件（`staging/last-run-status.json`），记录执行结果和时间
- 你每天花 1 分钟检查 status 文件
- 如果连续 N 天没有新的 staging 产出，手动去 check

更高级的方式（后续章节涉及）：

- 对接 Webhook 发通知到 Slack / 邮件
- 使用 OpenClaw 的 channels 功能

### 9.4.5 日志保存

每次 cron 执行的日志应该保留下来，至少保留 7 天。当你发现"昨天的日报质量很差"或"昨天的采集结果有问题"时，需要查看日志来定位原因。

## 9.5 你的第一批 Cron 任务设计

### 9.5.1 每日 AI 编程动态

| 项目 | 内容 |
|:---|:---|
| 名称 | `daily-ai-news` |
| 频率 | 每天 08:00 |
| Agent | news-watcher |
| 输入 | `/workspace/news-watcher/config/sources-ai.json` |
| 输出 | `/workspace/news-watcher/staging/ai-daily-{date}.json` |
| 去重 | 基于文章 URL |
| 失败策略 | 记录日志，不重试，等明天 |

### 9.5.2 每日日语教育产品动态

| 项目 | 内容 |
|:---|:---|
| 名称 | `daily-jp-edu-news` |
| 频率 | 每天 08:30 |
| Agent | news-watcher |
| 输入 | `/workspace/news-watcher/config/sources-jp-edu.json` |
| 输出 | `/workspace/news-watcher/staging/jp-edu-daily-{date}.json` |
| 去重 | 基于文章 URL |
| 失败策略 | 记录日志，不重试 |

### 9.5.3 每周 AWS 认证生态更新

| 项目 | 内容 |
|:---|:---|
| 名称 | `weekly-aws-cert-update` |
| 频率 | 每周一 09:00 |
| Agent | change-detector |
| 输入 | `/workspace/news-watcher/config/aws-cert-urls.json` |
| 输出 | `/workspace/news-watcher/staging/aws-cert-weekly-{date}.json` |
| 去重 | 基于页面内容哈希（对比上周快照） |
| 失败策略 | 记录日志，不重试 |

### 9.5.4 注意事项

- 不同任务的执行时间错开（08:00、08:30、09:00），避免同时竞争系统资源
- 先手动成功跑通每个任务至少 3 次后，再设为 cron
- 前两周每天检查 cron 的执行结果，确认稳定后再减少检查频率

## 9.6 Cron 故障排查

### 9.6.1 任务没触发

**可能原因：**
- Gateway 没有运行（cron 依赖 Gateway 来调度）
- Cron Job 定义有语法错误
- 时区设置不对（你设的 08:00 是 UTC，但你在 JST 时区）

**排查步骤：**
1. `claw health` → 确认 Gateway 存活
2. `claw cron list` → 确认任务存在
3. `claw cron status <job-name>` → 查看任务状态和下次触发时间
4. 检查系统时区和 cron 的时区配置

### 9.6.2 任务触发但失败

**可能原因：**
- 数据源不可用（网站宕机、RSS 地址变了）
- 模型 API 超时或错误
- 配置文件路径变了
- Sandbox 容器启动失败

**排查步骤：**
1. `claw logs` → 找到该次任务的执行日志
2. 查看错误信息判断是网络问题、模型问题还是配置问题
3. 手动跑一次同样的任务，看是否能复现

### 9.6.3 结果为空

**可能原因：**
- 数据源确实没有新内容（正常情况）
- 去重逻辑把所有内容都判为重复
- 抓取成功但模型没能提取出内容
- Agent 的 Prompt 和实际数据格式不匹配

**排查步骤：**
1. 检查数据源本身有没有内容
2. 临时关闭去重逻辑手动跑一次，看是否有输出
3. 查看日志中模型的原始返回内容

### 9.6.4 重复内容过多

**可能原因：**
- 去重逻辑没有生效
- 缓存文件（已处理 URL 列表）被清空或丢失
- 不同数据源之间有重复内容

**排查步骤：**
1. 检查去重用的缓存文件是否存在和正确
2. 对比两次输出中的 URL / ID 是否有重叠
3. 考虑增加跨源去重（基于标题相似度）

### 9.6.5 摘要质量差

**可能原因：**
- 使用的模型能力不足
- Prompt 不够精确
- 原始内容质量差（抓取到了广告、导航栏等无关内容）

**排查步骤：**
1. 查看原始抓取内容，判断是内容质量问题还是摘要生成问题
2. 如果是内容质量问题 → 优化抓取逻辑（更好的内容提取）
3. 如果是摘要质量问题 → 尝试换更强的模型，或优化 Prompt
