# 第 6 章：Agent 设计方法论

> **这一章解决什么问题？**
> 你已经能跑通 OpenClaw（第 4 章），知道了命令行的分层结构（第 5 章）。现在你需要回答一个关键问题：**我的 Agent 该怎么设计？**
> 很多人拿到 Agent 框架后，第一反应是写 Prompt——"你是一个 xxx 助手，帮我做 xxx"。但在 OpenClaw 的体系里，Prompt 只是 Agent 设计的一小部分。更重要的是：这个 Agent 的职责边界是什么？它的输入来自哪里？输出到哪里？它需要什么权限？失败了怎么办？
> 这一章教你一套系统化的 Agent 设计方法论。学完后，你面对任何任务都能用同一套框架来设计 Agent，而不是凭感觉临时拼凑。

---

## 6.1 什么叫一个"好 Agent"

### 6.1.1 五个评判标准

一个设计良好的 Agent 具备以下五个特征：

**1. 职责单一**

一个 Agent 只做一件事。"帮我抓取新闻并分析趋势并写报告并发邮件" ——这不是一个 Agent 的职责，这是四个 Agent 的协作链。

为什么职责单一如此重要？因为当一个 Agent 做的事情越多——

- 它接触的数据范围越广 → 权限越大 → 安全风险越高（回忆第 3 章）
- 它的失败模式越复杂 → 排障越困难
- 它的输出越不可预测 → 越难做质量校验
- 它越难被复用到其他场景

**2. 输入边界明确**

Agent 需要什么输入，必须清楚地定义出来。输入可以是：

- 一个目录路径（"读这个目录下的所有 Markdown 文件"）
- 一个 URL 列表（"访问这些网页"）
- 一个结构化数据文件（"读这个 JSON 文件里的记录"）
- 一条指令文本（"用这段 Prompt 来工作"）

**不好的输入定义：** "你去网上找找相关资料"——"网上"是哪里？"相关"是什么标准？"资料"是什么格式？全是模糊的。

**好的输入定义：** "读取 `/workspace/news-watcher/sources.json` 中定义的 RSS 源列表，抓取每个源的最新 10 篇文章"——来源明确、范围明确、数量明确。

**3. 输出格式固定**

Agent 的输出必须是确定性的格式。这意味着你在设计阶段就要决定：

- 输出是 JSON 还是 Markdown 还是 CSV？
- JSON 的 schema 是什么？有哪些必填字段？
- 输出文件保存在哪个目录？文件名的命名规则是什么？

为什么输出格式必须固定？因为 Agent 的输出往往是另一个 Agent 的输入、或者是 importer 的输入、或者是你人工审核的对象。如果输出格式不确定，下游所有环节都无法依赖。

**4. 失败可回滚**

Agent 可能失败——模型理解错了指令、网络中断、抓取被拒绝、输出格式异常。当失败发生时，系统的状态不应该比执行前更差。

这意味着：

- Agent 的写入应该写到 staging 目录，不是直接写到 production 目录
- Agent 不应该在中途删除已有数据
- Agent 的操作应该有日志记录，以便事后审计

**5. 不依赖隐性上下文**

一个好的 Agent 不应该依赖"你脑子里知道但没有写进配置里"的信息。它需要的所有上下文——数据源、输出位置、格式要求、权限限制——都应该明确地写在 Agent 定义或相关配置文件中。

这样做的好处：别人（或者三个月后的你自己）看到这个 Agent 的定义，不需要额外解释就能理解它在做什么。

### 6.1.2 反面案例

**一个"坏 Agent"的设计：**

> 名称：my-helper  
> 职责：帮我处理各种任务  
> 输入：用户每次告诉它  
> 输出：看情况  
> 权限：给满  

这个设计的问题：职责不单一（"各种任务"）、输入不明确（"每次告诉它"）、输出不固定（"看情况"）、权限过大（"给满"）。

**改进后的设计：**

> 名称：news-collector  
> 职责：从指定 RSS 源抓取最新文章并生成摘要  
> 输入：`/workspace/news-watcher/sources.json`（RSS 源列表）  
> 输出：`/workspace/news-watcher/staging/daily-{date}.json`（每日摘要 JSON）  
> 权限：读（sources.json）+ 写（staging 目录）+ 网络（仅 RSS 源域名）  
> 失败策略：如果某个 RSS 源抓取失败，跳过该源、记录错误日志，继续处理其他源

## 6.2 角色化设计

### 6.2.1 为什么要给 Agent 定角色

在你的实际使用场景中，你需要 Agent 完成的工作涵盖多个方向——信息采集、内容整理、定时巡检、代码原型、数据导入。如果每次都临时设计 Agent，会导致：

- Agent 定义散乱、难以管理
- 权限设计无章可循
- 输出格式不统一
- 失败策略不一致

角色化设计就是把你的需求抽象成几个标准角色，每个角色有固定的能力模型和约束。新任务来了，先判断"这属于哪个角色的工作"，然后基于该角色的模板来创建或配置 Agent。

### 6.2.2 五个基础角色

以下五个角色覆盖了学习阶段的大部分需求：

#### Collector（采集员）

**职责：** 从外部数据源收集信息，转换为结构化数据。

**典型任务：**
- 抓取 RSS 新闻源
- 抓取网页内容并提取字段
- 收集 API 返回的数据

**输入：** 数据源列表（URL、RSS 地址、API endpoint）
**输出：** 结构化 JSON/CSV 文件
**权限：** 读（配置文件）+ 写（staging 目录）+ 网络（指定域名）
**模型选择：** 中低级别模型，任务模式固定
**是否需要 Sandbox：** 推荐。采集涉及网络访问，有数据外泄风险。

#### Curator（整理员）

**职责：** 对已有数据进行清洗、分类、格式化、模块化编排。

**典型任务：**
- 将采集到的原始数据清洗和标准化
- 将学习资料按主题和难度分类
- 生成课程模块大纲

**输入：** staging 目录中的原始数据文件
**输出：** validated 目录中的清洗后数据文件，或 Markdown 格式的模块文档
**权限：** 读（staging 目录）+ 写（validated 目录）
**模型选择：** 中高级别模型，需要理解内容语义
**是否需要 Sandbox：** 看情况。如果只做读写操作，可以不用。如果整理过程涉及执行脚本，需要 Sandbox。

#### Watcher（巡检员）

**职责：** 定期检查某些条件、生成状态报告。

**典型任务：**
- 每天检查 AI 编程领域的最新动态
- 每天检查日语教育领域的产品更新
- 每周检查 AWS 认证考试的变更

**输入：** 巡检规则配置文件（关注领域、关键词、来源列表）
**输出：** 日报/周报 Markdown 文件
**权限：** 读（配置文件 + 历史报告）+ 写（报告目录）+ 网络
**模型选择：** 中级别模型，摘要和筛选不需要太强的推理能力
**是否需要 Sandbox：** 推荐。涉及网络访问。

#### Prototyper（原型员）

**职责：** 根据需求描述，生成代码原型、页面骨架、测试用例草稿。

**典型任务：**
- 生成汉字检定搜索页的前端代码骨架
- 生成 API 接口的 mock 数据
- 生成测试用例的初始版本

**输入：** 需求描述文件（Markdown 或 JSON 格式的功能需求）
**输出：** 代码文件、预览页面、测试文件
**权限：** 读（需求文件）+ 写（原型目录）+ 执行（可能需要运行代码做 preview）
**模型选择：** 高级别模型，代码生成需要准确性
**是否需要 Sandbox：** 必须。原型员需要执行权限，必须在容器中运行。

#### Executor（执行员）

**职责：** 执行确定性的数据导入、文件迁移、格式转换。

**典型任务：**
- 把 validated 目录下的数据导入到测试数据库
- 把原型代码从 staging 移动到项目目录
- 执行批量的文件格式转换

**输入：** validated 目录下的数据文件 + 执行配置
**输出：** 数据库记录 / 目标目录下的文件
**权限：** 读（validated 目录）+ 写（目标目录或数据库）+ 执行（运行导入脚本）
**模型选择：** 取决于任务复杂度。简单的文件移动用小模型，涉及数据转换逻辑的用中级模型
**是否需要 Sandbox：** 推荐。涉及执行权限和可能的数据库写入。

### 6.2.3 角色分工速查表

| 角色 | 核心动作 | 输入来源 | 输出去向 | 风险级别 |
|:---|:---|:---|:---|:---|
| Collector | 抓取 | 外部数据源 | staging/ | 中 |
| Curator | 清洗/整理 | staging/ | validated/ | 低-中 |
| Watcher | 巡检/报告 | 外部 + 配置 | reports/ | 中 |
| Prototyper | 生成代码 | 需求文件 | prototype/ | 高 |
| Executor | 导入/迁移 | validated/ | 目标系统 | 高 |

## 6.3 任务拆解方法

### 6.3.1 七步任务定义法

当你拿到一个新任务时，用以下七个步骤来拆解：

**第一步：目标（Goal）**

用一句话描述这个任务要达成什么结果。不要描述过程，描述终态。

- 好的目标："获得今天 AI 编程领域的 10 条最新动态摘要"
- 不好的目标："去网上搜索一下 AI 编程相关内容"

**第二步：输入（Input）**

明确列出任务执行需要的所有输入数据和配置。

- 数据源在哪里？是文件、URL、API？
- 配置参数是什么？关键词列表、时间范围、数量限制？
- 这些输入已经存在了，还是需要先准备？

**第三步：工具（Tools）**

这个任务需要 Agent 使用什么能力？

- 需要读取文件？
- 需要访问网络？
- 需要执行命令？
- 需要写入文件？

每一种能力对应一种权限。权限越多，风险越高，隔离要求越严。

**第四步：步骤（Steps）**

把任务分解成有序的具体操作步骤。

例如，"抓取 AI 编程动态"可以分解为：

1. 读取 sources.json 中的 RSS 源列表
2. 逐个访问 RSS 源，获取最新 10 篇文章的标题和链接
3. 对每篇文章获取正文内容
4. 对每篇文章生成 50 字以内的中文摘要
5. 将所有摘要合并为一个 JSON 文件
6. 保存到 staging 目录

**第五步：输出（Output）**

明确定义输出的格式和位置。

```json
{
  "date": "2025-01-15",
  "source_count": 5,
  "article_count": 10,
  "articles": [
    {
      "title": "文章标题",
      "url": "https://example.com/article",
      "source": "RSS 源名称",
      "summary": "50 字以内的摘要",
      "published_at": "2025-01-15T08:00:00Z"
    }
  ]
}
```

输出文件路径：`/workspace/news-watcher/staging/daily-2025-01-15.json`

**第六步：校验（Validation）**

如何判断任务执行成功？

- 输出文件是否存在？
- JSON 格式是否合法？
- 文章数量是否在合理范围内（不为 0，不超过预期上限）？
- 摘要是否是有意义的中文文本（不是乱码或空字符串）？

**第七步：失败处理（Failure Handling）**

如果任务失败或部分失败，怎么办？

- 某个 RSS 源不可访问 → 跳过该源，记录错误日志，继续处理其他源
- 所有 RSS 源都失败 → 输出一个空结果文件 + 生成告警日志
- 输出 JSON 格式异常 → 不覆盖之前的输出文件，保留本次的错误输出到 error 目录

### 6.3.2 任务定义模板

你可以为每个 Agent 创建一个任务定义文件（Markdown 或 YAML），包含以上七个部分。以下是一个 Markdown 模板：

```markdown
# Agent 任务定义

## 目标
[一句话描述终态]

## 输入
- 数据源：[路径/URL/配置文件]
- 参数：[关键配置]

## 工具需求
- [ ] 文件读取
- [ ] 文件写入
- [ ] 网络访问
- [ ] 命令执行

## 执行步骤
1. [步骤 1]
2. [步骤 2]
3. ...

## 输出
- 格式：[JSON/Markdown/CSV]
- 路径：[输出文件路径]
- Schema：[字段定义]

## 校验条件
- [条件 1]
- [条件 2]

## 失败处理
- 场景 A → 处理方式 A
- 场景 B → 处理方式 B
```

## 6.4 Prompt 不是唯一重点

### 6.4.1 为什么 Operator 设计比 Prompt 更重要

很多教程和文章给人一个印象："Agent 用得好不好，关键在于 Prompt 写得好不好。" 这在某些场景下是对的——比如你用 ChatGPT 聊天时，Prompt 确实是唯一的控制手段。

但在 OpenClaw 这样的 Operator 框架中，Prompt 只是 Agent 执行流程中的一个环节。更重要的控制手段包括：

- **权限设计**：Agent 能做什么、不能做什么
- **目录隔离**：Agent 能访问哪些数据
- **输出 Schema**：Agent 的产出必须符合什么格式
- **工具限制**：Agent 能使用哪些工具
- **Approval 设置**：哪些操作需要人工确认

即使你的 Prompt 写得不够精确，只要权限和输出 Schema 设计得好，Agent 的"犯错范围"也是有限的。反过来，即使你的 Prompt 写得完美，如果权限给满了、没有目录隔离、没有输出校验——一个小误解就可能导致严重后果。

### 6.4.2 为什么权限和输出 Schema 比文案更重要

**权限是硬约束，Prompt 是软约束。**

Prompt 告诉模型"你应该做什么"——模型"大概率"会遵守，但不保证。模型可能误解 Prompt、产生幻觉、或者在边界情况下做出出乎意料的判断。

权限是系统级别的强制限制——如果 Agent 没有网络权限，它就是访问不了互联网，无论 Prompt 怎么写。如果 Agent 只有特定目录的写权限，它就是写不到其他地方。

**输出 Schema 是质量的底线。**

如果你要求 Agent 输出一个包含 `title`、`url`、`summary`、`date` 四个字段的 JSON，那么即使模型的理解不完美，输出也至少会有一个固定的结构可以被下游系统解析。如果没有 Schema 约束，Agent 可能今天输出 JSON、明天输出 Markdown、后天输出纯文本——下游系统全都要崩溃。

**设计优先级：**

```
1. 权限设计（能做什么）   → 安全底线
2. 输出 Schema（产出什么） → 质量底线
3. 目录隔离（在哪里做）   → 影响范围
4. 失败处理（出错怎么办） → 可维护性
5. Prompt（怎么做）       → 效果优化
```

### 6.4.3 Prompt 设计的基本原则

虽然 Prompt 不是最重要的，但它仍然值得认真对待。以下是几条实用原则：

**明确角色**：告诉模型它扮演什么角色。"你是一个新闻摘要生成助手"比"帮我处理一些新闻"更好。

**明确输入**：告诉模型输入是什么格式。"你会收到一个 JSON 数组，每个元素包含 title 和 content 字段"。

**明确输出**：告诉模型输出要什么格式。"你的输出必须是 JSON 格式，包含 summary 和 keywords 两个字段"。

**明确约束**：告诉模型不能做什么。"不要编造不存在的信息。如果原文没有提供某个字段的值，用 null 填充。"

**简洁**：Prompt 不需要很长。把复杂逻辑放在 Agent 的步骤定义和工具配置中，Prompt 只需要传达核心指令。

## 6.5 你的 Agent 初始分工设计

### 6.5.1 资讯巡检 Agent

**对应角色：** Watcher + Collector

**任务描述：** 每天从指定的 RSS 源和网站抓取 AI 编程、日语教育领域的最新动态，生成中文摘要。

**设计草案：**

| 项目 | 内容 |
|:---|:---|
| 名称 | `news-watcher` |
| 输入 | `/workspace/news-watcher/config/sources.json` |
| 输出 | `/workspace/news-watcher/staging/daily-{date}.json` |
| 权限 | 读配置 + 写 staging + 网络 |
| 模型 | 中级（摘要任务不需要最强模型） |
| 隔离 | Sandbox（涉及网络访问） |
| 频率 | 每日一次 |

### 6.5.2 汉字检定采集 Agent

**对应角色：** Collector

**任务描述：** 从指定的数据源采集汉字检定相关资料，提取字段（汉字、级别、音读、训读等），生成结构化 JSON。

**设计草案：**

| 项目 | 内容 |
|:---|:---|
| 名称 | `kanji-collector` |
| 输入 | `/workspace/kanji-staging/config/sources.json` |
| 输出 | `/workspace/kanji-staging/staging/raw-{source}-{date}.json` |
| 权限 | 读配置 + 写 staging + 网络 |
| 模型 | 中高级（日语字段抽取需要语言理解能力） |
| 隔离 | Sandbox |
| 频率 | 按需手动触发（不适合高频自动抓取） |

### 6.5.3 课程整理 Agent

**对应角色：** Curator

**任务描述：** 将采集到的学习资料按主题、难度分类，生成课程模块大纲和 Lesson 草稿。

**设计草案：**

| 项目 | 内容 |
|:---|:---|
| 名称 | `course-curator` |
| 输入 | `/workspace/course-builder/staging/` （已采集的原始资料） |
| 输出 | `/workspace/course-builder/validated/` （模块化课程草稿） |
| 权限 | 读 staging + 写 validated |
| 模型 | 高级（课程设计需要创造性和教学逻辑） |
| 隔离 | 不强制（只做文件读写，不涉及网络和执行） |
| 频率 | 按需手动触发 |

### 6.5.4 原型验证 Agent

**对应角色：** Prototyper

**任务描述：** 根据功能需求描述，生成前端代码骨架、mock 数据、基础页面。

**设计草案：**

| 项目 | 内容 |
|:---|:---|
| 名称 | `prototype-builder` |
| 输入 | `/workspace/prototype-lab/requirements/` （需求文件） |
| 输出 | `/workspace/prototype-lab/output/` （代码文件） |
| 权限 | 读需求 + 写 output + 执行（运行代码 preview） |
| 模型 | 高级（代码生成需要准确性） |
| 隔离 | 必须 Sandbox（涉及执行权限） |
| 频率 | 按需手动触发 |

```
               ┌─────────────┐
外部数据 ────→ │  Collector   │ ────→ staging/
               └─────────────┘
                                       │
               ┌─────────────┐         ↓
               │   Curator    │ ← ─ staging/
               └─────────────┘
                      │
                      ↓
                 validated/
                      │
               ┌──────┴──────┐
               ↓              ↓
         课程模块        数据库入库
         (第11章)        (第12章)

               ┌─────────────┐
需求描述 ────→ │  Prototyper  │ ────→ prototype/
               └─────────────┘

               ┌─────────────┐
配置文件 ────→ │   Watcher    │ ────→ reports/
               └─────────────┘
```

注意：这四个 Agent 是独立工作的，它们之间通过文件系统（staging → validated → production）来传递数据，而不是直接互相调用。这种解耦设计让你可以单独调试、替换、升级任何一个 Agent，而不影响其他的。

## 6.6 如果这里失败，先检查什么

**"我不知道我的任务应该由哪个角色来做"**
→ 问自己三个问题：(1) 这个任务的输入来自外部还是系统内部？外部 → Collector 或 Watcher。(2) 这个任务主要是"转换数据"还是"生成代码"？转换 → Curator，生成 → Prototyper。(3) 这个任务是一次性的还是定期的？定期 → Watcher，一次性 → 对应角色。

**"我不确定七步拆解法的某一步该怎么填"**
→ 如果你在"输入"步骤卡住了，说明你还不确定数据从哪里来——先解决数据源问题。如果在"输出"步骤卡住了，说明你还没想好这个任务的产出是什么——先定义终态。如果在"校验"步骤卡住了，问自己"如果 Agent 给了一个完全错误的输出，我怎么发现？"

**"我觉得设计太复杂了，能不能直接写 Prompt 就开始用？"**
→ 可以。但在这之前至少回答三个问题：(1) 它的输出保存在哪里？(2) 它有什么权限？(3) 如果输出完全错误，会造成什么后果？如果后果可以接受（比如只是一个临时实验），那就直接跑。如果后果不可接受（比如会覆盖重要文件），那花 10 分钟做个最小设计。
