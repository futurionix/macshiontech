# 第 15 章：安全审计与长期治理

> **这一章解决什么问题？**
> 第 3 章教你在一开始就建立安全观——最小权限、信任边界、六条红线。但安全不是一次性的工作。随着你使用 OpenClaw 的时间越来越长、Agent 越来越多、自动化流程越来越复杂，系统的安全状态会悄悄退化。
> 这一章教你两件事：**如何发现安全退化**，以及**如何建立长期治理机制**。学完后你能定期评估系统安全状态，确保半年后的安全水平不低于第一天。

---

## 15.1 为什么长期使用比第一次配置更危险

### 15.1.1 权限会慢慢变大

你一开始给 collector 的权限是"只读网络 + 写入 staging 目录"。三个月后你可能经历了这些场景：

- 某次采集需要先清理旧文件——给了删除权限，后来忘记收回
- 某次调试需要 Agent 执行 Shell 命令——临时开放了执行权限，调试完没关
- 新增了一个源需要写入另一个目录——直接把整个 Workspace 的写权限都打开了

每一次都有合理的理由，但累积起来，你的 Agent 权限已经远超最初的设计。

**这就是"权限膨胀"（Permission Creep）。**

### 15.1.2 Skills 会慢慢变多

你可能在社区找到一个好用的 Skill——"自动提取网页正文"，装了。又找到一个——"批量重命名文件"，也装了。半年后你有 20 个 Skill，但你已经忘记其中一半是从哪里来的、做了什么、有没有安全审查。

每一个 Skill 都是你信任边界内的代码。来源不明的 Skill 和来源不明的 npm 包一样危险。

### 15.1.3 Workspace 会慢慢混乱

最初你的目录结构很清晰——`staging/`、`validated/`、`production/` 分层明确。但随着时间推移：

- 调试用的临时文件留了下来
- 不同 Agent 的输出混在了同一个目录
- 废弃的旧数据没有清理

混乱的 Workspace 增加了安全风险——当你分不清哪些文件是重要的、哪些是临时的，你就无法有效地设置权限边界。

### 15.1.4 你会慢慢放松警惕

第一天你会仔细审查每一个 Agent 的输出。三个月后你只看一下标题就通过了。半年后你连标题都不看了——"反正一直都正常"。

**安全的最大敌人不是技术漏洞，而是人的惰性。**

## 15.2 定期安全检查清单

每月做一次安全检查。不需要很复杂——花 15 分钟过一遍这个清单就够了：

### 15.2.1 权限审计

**检查问题：** 哪些 Agent 有超出其职责的权限？

```
检查每个 Agent 的安全配置文件，回答以下问题：
- 这个 Agent 有执行权限吗？它需要吗？
- 这个 Agent 能写入哪些目录？是否超出了它的职责范围？
- 这个 Agent 能进行网络请求吗？它需要访问哪些域名？
- 这个 Agent 上次权限变更是什么时候？原因是什么？
```

**怎么做：**

| Agent | 当前权限 | 是否必需 | 操作 |
|-------|---------|---------|------|
| collector-ai-news | 读网络 + 写 staging | 是 | 维持 |
| collector-jp-news | 读网络 + 写 staging + 删除旧文件 | 删除权限可以收回 | 收回删除权限 |
| curator-kanji | 读 staging + 写 validated + Shell 执行 | Shell 执行不需要 | 收回执行权限 |

### 15.2.2 Secrets 审计

**检查问题：** 哪些 Agent 能访问 Secrets？Secrets 是否过期？

```
- 列出所有存储的 Secrets
- 每个 Secret 被哪些 Agent 引用？
- 有没有不再使用但仍然存在的 Secret？
- API Key 是否需要轮换（rotate）？
```

**建议：** API Key 至少每 90 天轮换一次。如果某个 API Key 已经超过 90 天没有更换，安排一次轮换。

### 15.2.3 Workspace 审计

**检查问题：** Workspace 是否仍然整洁、边界清晰？

```
- 有没有不属于任何 Agent 的临时文件？→ 清理
- 有没有混在正式数据中的调试文件？→ 移走或删除
- 目录结构是否仍然符合最初的设计？→ 如有偏离，恢复
- 各 Agent 的 Workspace 权限映射表是否仍然准确？→ 更新
```

### 15.2.4 Cron 审计

**检查问题：** 所有定时任务是否仍在按预期运行？

```
- 列出所有活跃的 Cron 任务
- 每个任务最后一次成功执行是什么时候？
- 有没有失败了但没有被注意到的任务？
- 有没有不再需要但仍在运行的任务？→ 停止
```

### 15.2.5 Skill 审计

**检查问题：** 所有已安装的 Skill 是否仍然可信？

```
- 列出所有已安装的 Skill
- 每个 Skill 的来源是哪里？（官方 / 社区 / 自建）
- 有没有来源不明的 Skill？→ 评估或移除
- 有没有不再使用的 Skill？→ 卸载
```

## 15.3 Secrets 与 Approvals 的边界

### 15.3.1 什么应该放 Secrets

Secrets 存储敏感信息——这些信息如果泄露会造成直接损失：

- **API Key / Token：** OpenAI API Key、数据库连接字符串、第三方服务的访问令牌
- **密码：** 任何需要认证的系统密码
- **私钥：** SSH 私钥、签名密钥

**不应该放在 Secrets 中的东西：**
- 配置参数（模型名称、温度参数）——这些不是敏感信息
- 文件路径——不需要加密保护
- 公开的 URL——不是秘密

### 15.3.2 什么应该需要人工 Approval

Approval 机制让你在 Agent 执行高风险操作前有一个"确认"的机会：

**必须 Approval 的操作：**
- 写入生产数据库
- 删除文件（特别是生产目录下的文件）
- 发送外部通知（邮件、消息推送）
- 安装新依赖（在 Sandbox 外）
- 修改系统配置

**不需要 Approval 的操作：**
- 读取公开数据源
- 写入 staging 目录
- 在 Sandbox 内执行命令（已经有容器隔离）
- 生成日志

### 15.3.3 什么不能默认自动批准

有些操作你可能习惯性地自动批准——"反正每次都会通过"。这很危险。以下操作**永远不要设置自动批准**：

- **生产数据库写入** — 即使 importer 每天都在导入，每次仍然应该有人确认导入内容
- **文件删除** — 误删不可恢复（除非有备份）
- **Secrets 读取** — 每次 Agent 请求 Secret 时你都应该知道原因
- **新网络连接** — Agent 突然要访问一个新 URL，你需要评估是否安全

## 15.4 持续治理原则

### 15.4.1 高风险任务单独 Gateway

官方安全文档明确强调：按信任边界拆分 Gateway 和部署单元。

如果你的系统中有高风险操作（比如写生产数据库、访问敏感 API），把这些操作放在一个独立的 Gateway 实例上：

```
Gateway A（低风险）
├── collector-ai-news（只读网络）
├── collector-jp-news（只读网络）
└── curator-kanji（只读写文件）

Gateway B（高风险）
├── importer-kanji（写生产数据库）
└── prototyper（执行代码）
```

**为什么要拆分？**

如果低风险 Gateway 被攻破（比如某个 Agent 的 Prompt 被注入了恶意指令），攻击者只能接触到新闻采集数据——无法访问生产数据库和代码执行权限。

### 15.4.2 高风险任务单独主机

更进一步——高风险的 Gateway 可以运行在一台独立的机器上。物理隔离比逻辑隔离更安全。

对于个人学习者来说这可能过于复杂，但概念要理解：当风险足够高时，隔离级别应该从"进程级"升级到"主机级"。

### 15.4.3 高风险任务单独身份

每个 Gateway 实例应该使用独立的 API Key 和凭证：

- Gateway A 使用 API Key A — 只有资讯采集需要的权限
- Gateway B 使用 API Key B — 只有数据库写入需要的权限

一个 Key 泄露不会影响另一个 Gateway 的安全。

### 15.4.4 低风险任务可集中管理

不是所有东西都需要拆得很细。低风险的 Agent（只读数据、只写 staging）可以共享同一个 Gateway。过度拆分会增加管理复杂度——在安全和便利之间找到平衡。

**判断标准：** 如果这个 Agent 被攻破，最坏的结果是什么？如果最坏结果是"丢了今天的新闻摘要"，那就是低风险；如果最坏结果是"生产数据库被清空"，那就是高风险。

## 15.5 安全退化的信号

以下信号表示你的安全状态正在退化——看到这些信号时应该立刻安排一次安全检查：

| 信号 | 意味着什么 | 应该做什么 |
|------|----------|----------|
| 你已经不记得某个 Agent 有哪些权限 | 权限管理失控 | 做一次完整的权限审计 |
| 你给 Agent 加了权限但没记录原因 | 变更缺少追踪 | 建立权限变更日志 |
| 有 Agent 在用但你已经忘了它的配置 | Agent 管理失控 | 整理 Agent 清单 |
| 你最后一次安全检查是两个月前 | 审计频率不够 | 重新建立月度检查习惯 |
| 你在生产环境调试时临时放宽了权限 | 临时权限未收回 | 立刻回收临时权限 |

## 15.6 如果这里失败，先检查什么

**"不知道从哪里开始做安全审计"**
→ 从权限审计开始——它是最直接的。列出所有 Agent，记录每个 Agent 的权限，标注哪些权限可能是多余的。

**"做了审计但不确定哪些权限应该收回"**
→ 问自己一个问题："如果这个 Agent 没有这个权限，它的核心任务还能完成吗？"如果答案是"能"，收回这个权限。

**"团队成员反对收紧权限（太麻烦了）"**
→ 解释"权限膨胀"的累积风险。每一次"方便"的权限放宽都在增加攻击面。安全的代价是一些不便，不安全的代价可能是数据泄露。

**"觉得拆分 Gateway 太复杂了"**
→ 你不需要一开始就拆分。先用一个 Gateway 跑，但从一开始就**把高风险 Agent 和低风险 Agent 的权限分开配置**。等规模变大时，拆分 Gateway 就是一个自然的下一步。
